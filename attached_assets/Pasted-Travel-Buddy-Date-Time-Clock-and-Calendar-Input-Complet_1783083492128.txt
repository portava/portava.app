Travel Buddy — Date, Time, Clock, and Calendar Input Completion Pass

Wire clocks, calendars, date pickers, time pickers, timezone handling, and calendar integrations across the entire app.

Users should NOT be required to manually type dates or times anywhere in the app.

Do not rebuild unrelated systems.
Do not redesign full screens unless required to replace manual date/time entry.
Do not touch unrelated backend logic unless date/time storage or validation requires it.
Do not add fake calendar behavior.
Do not create fake success.
Do not leave broken date/time fields that accept invalid manual text.

Goal:
Every date/time function in Travel Buddy must use a proper calendar, clock, picker, or structured selector.

Users should be able to choose:
- dates from a calendar picker
- times from a clock/time picker
- date ranges from a date-range picker
- recurring availability from a visual schedule grid or time-range picker
- timezone-aware trip/event/meetup times
- calendar export/add-to-calendar where already part of the feature
- reminders and schedule-based flows without manual typing

Manual text entry should be removed, disabled, or replaced everywhere a user is expected to enter a date or time.

Required UX rules:

1. No manual typing for date/time fields.
   Replace text inputs with:
   - calendar date picker
   - clock time picker
   - date range picker
   - duration picker
   - recurring availability grid
   - dropdown/select for common intervals
   - native calendar/event picker if appropriate

2. Keep manual fallback only if required by platform limitations.
   If a fallback is needed:
   - validate strictly
   - show clear format
   - prefer hidden developer fallback over user-facing manual typing

3. Use native/mobile-friendly pickers.
   Prefer existing project dependencies first.
   If date/time picker library already exists, use it.
   If no picker exists, inspect Expo/React Native setup and choose the smallest safe dependency only if necessary.

4. Timezone handling must be correct.
   - Store timestamps in UTC or existing backend standard.
   - Display in the user’s local timezone unless the event/trip has a destination timezone.
   - For trips/events in another city, show destination timezone where useful.
   - Avoid ambiguous times.
   - Include timezone label when needed.
   - Do not shift all-day dates incorrectly.

5. Date range rules:
   - End date cannot be before start date.
   - End time cannot be before start time unless overnight is intentionally supported.
   - Trip end date cannot be before trip start date.
   - Booking end time/duration must be valid.
   - Meetup poll slots must be future times.
   - Safe Return check-ins must use valid future intervals.

6. Duration rules:
   Use structured duration controls:
   - 15 min
   - 30 min
   - 1 hour
   - 2 hours
   - custom picker only if needed

7. Calendar integration:
   Audit visible “Add to Calendar” actions.
   If already visible:
   - wire to native calendar export or .ics/share flow if feasible
   - request permission honestly
   - show success only after calendar action succeeds
   - show unavailable copy if not supported
   - do not fake calendar add success

8. Display formatting:
   Standardize:
   - Today / Tomorrow where appropriate
   - Month day, year for future trips/events
   - Localized 12-hour time for current user preference/location
   - timezone abbreviation/label when needed
   - relative time for feeds/messages
   - absolute time in detail screens

9. Accessibility:
   - date/time picker buttons must have labels
   - selected dates/times must be readable
   - error states must be clear
   - keyboard should not block picker controls

Implementation rules:

1. Create reusable components if needed:
   - DatePickerField
   - TimePickerField
   - DateRangePickerField
   - DateTimePickerField
   - DurationPickerField
   - AvailabilityGrid
   - TimezoneLabel
   - AddToCalendarButton

2. Use these reusable components across screens instead of one-off picker code.

3. Do not change backend date formats unless required.
   If backend already expects ISO strings, keep ISO strings.
   Convert picker values to ISO safely before submit.

4. If backend lacks timezone field but screen needs timezone-aware display:
   - use user/device timezone for display
   - use destination timezone only if already available from trip/event data
   - document any remaining limitation

5. Do not introduce fake calendar sync.
   Calendar add must either:
   - actually create/export a calendar event,
   - open native calendar/share flow,
   - or be honestly disabled.

6. Preserve existing validation.
   Add missing validation only where date/time picker now controls the field.

Fix only proven issues:
- manual date/time text entry
- invalid date/time accepted
- end before start
- fake calendar success
- dead Add to Calendar button
- wrong timezone display
- date formatting inconsistency that confuses users
- visible date/time action with no handler
- backend/frontend mismatch for date/time fields

Do not fix:
- unrelated layout polish
- new reminder systems not already visible
- new recurring event engine unless existing availability/meetup system needs it
- full Google Calendar sync unless already in scope
- full external calendar account connection

Production/database considerations:
1. Confirm schema has timezone fields where code expects them.
2. Confirm duration/date/time columns exist where backend routes use them.
3. Confirm migrations are applied for meetup/event/trip date tables.
4. If a date/time column is missing for a live field, mark as blocker and add/apply the smallest migration only if necessary.
5. Do not claim production is ready unless verified.
