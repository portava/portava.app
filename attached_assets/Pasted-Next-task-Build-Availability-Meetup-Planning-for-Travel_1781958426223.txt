Next task: Build Availability + Meetup Planning for Travel Buddy.

Goal:
Allow users to share when they are free, coordinate meetups from trip/circle chat, and add accepted meetups into a trip plan.

Core product rule:
Availability should help people coordinate, but it must not expose sensitive location, live location, private schedules, or trip access without permission.

Relationship model:
- Follow = public discovery
- Friend = mutual social connection
- Circle = trusted privacy/live-map access
- Trip member = trip-specific access
- Availability = user-controlled time-sharing
- Meetup = planned event/invite

Hard rule:
Availability does not grant:
- trip membership
- circle membership
- live location
- exact GPS
- private Passport access
- private posts

SECTION 1 — Availability types

Support:

1. General weekly availability
User can set recurring free times.

Example:
- Monday evening
- Friday night
- Saturday afternoon

2. Trip-specific availability
User can set free time for a specific trip.

Example:
- “Free in Taipei Friday 8 PM–12 AM”
- “Available Saturday afternoon during this trip”

3. Quick status availability
User can mark:
- Free now
- Free tonight
- Free this weekend
- Busy
- Open to plans

Do not overbuild calendar-level scheduling yet.

SECTION 2 — Availability privacy

Availability visibility options:
- private
- friends
- trusted circle
- trip members
- public limited

Default:
- private unless user actively shares it

Trip-specific availability:
- visible only to accepted trip members by default

Circle availability:
- visible only to accepted circle members

Public limited:
- can show broad status like “Open to meetups tonight”
- must not show exact schedule unless user allows it

Rules:
- exact schedule should not be public by default
- live location is separate and must not be inferred from availability
- availability does not expose hotel/address/location

SECTION 5 — Trip availability editor

Inside a trip:
Add “Availability” section.

Trip members can:
- mark when they are free during trip dates
- see overlapping availability of accepted trip members
- propose meetup based on overlap

Trip availability should show:
- who is free
- day/time blocks
- best overlap windows
- timezone
- “Create meetup” button

Non-members:
- cannot see trip availability

Pending invite:
- cannot see trip availability until accepted

SECTION 6 — Circle availability

Inside trusted circle:
Members can optionally share availability with circle.

Circle availability should show:
- quick status
- recurring availability if shared
- upcoming free windows if shared

Circle availability must only show to accepted circle members.

SECTION 8 — Meetup RSVP

- Going
- Maybe
- Can’t go

Organizer can see:
- going count
- maybe count
- declined count
- pending count

Rules:
- only invited users or trip/circle members can RSVP depending on meetup visibility
- non-invited public users cannot RSVP to private meetups
- trip meetups only visible to accepted trip members unless public explicitly later

SECTION 9 — Time poll

Support simple time voting.

Organizer can suggest multiple time options.

Users vote:
- yes
- maybe
- no

UI:
- show best time
- show votes
- allow organizer to confirm final time

Do not overbuild full Doodle-style scheduling in first pass.

SECTION 10 — Add meetup to trip plan

If meetup belongs to a trip:
- allow “Add to trip plan”
- create trip plan item using existing trip plan model if available
- preserve source: meetup_id
- show in trip itinerary/plan

Rules:
- only trip owner/admin or allowed members can add to plan
- do not duplicate plan items
- if meetup time changes, update linked plan item or show sync warning

SECTION 11 — Chat integration

Trip/circle chat should support meetup cards.

When a meetup is created from chat:
- post a system card into chat:
  “Meetup proposed: Dinner in Ximending, Friday 8 PM”
- users can RSVP from card
- updates show in chat:
  “Andre is going”
  “Time confirmed: Friday 8 PM”

Do not spam chat with every minor change.
Use compact update cards.

Actions:
- Going
- Maybe
- Can’t go

- include meetup invites if user action is needed

SECTION 13 — Privacy rules

Availability must not expose:
- exact GPS
- live location
- hotel address
- private trip details to non-members
- private circle details to non-members
- private schedule to public
- hidden profile data

Meetups must not expose:
- private trip/circle details to outsiders
- invitee list publicly unless product allows
- exact GPS unless place is public and user chose it

- GET /api/circles/:circleId/availability
- PATCH /api/circles/:circleId/availability

Meetups:

- GET /api/meetups/:meetupId
- PATCH /api/meetups/:meetupId
- DELETE /api/meetups/:meetupId
- POST /api/meetups/:meetupId/invites
- POST /api/meetups/:meetupId/rsvp

- POST /api/meetups/:meetupId/confirm-time
- POST /api/meetups/:meetupId/add-to-trip-plan

Security:
- resolve current user from auth token
- never trust client user_id
- verify trip/circle membership before reading/writing scoped availability
- verify meetup visibility before reading
- verify invite/recipient before RSVP
- service-role key never exposed
