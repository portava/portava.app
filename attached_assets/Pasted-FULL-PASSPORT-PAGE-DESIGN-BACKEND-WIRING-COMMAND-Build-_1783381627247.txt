FULL PASSPORT PAGE DESIGN + BACKEND WIRING COMMAND

Build the full mobile Passport page to match the approved design direction exactly, while keeping the app’s existing color scheme, dark mode, neon teal/mint accent system, current typography, current icon style, current rounded card language, current bottom navigation, and current backend architecture.

This is not just a verification-stamp patch. This is a full Passport page implementation and wiring pass.

Do not rebuild the app. Do not change the global theme. Do not rename main tabs. Do not create fake standalone UI that is disconnected from backend data. This must use real profile, trust, stamps, postcards, plans, follow, and verification data wherever those systems already exist.

The Passport page should feel like a premium digital travel identity: part profile, part passport, part trust card, part travel memory board.

DESIGN STYLE

Use this design pattern:

“Digital Passport + Social Travel Identity + Trust Proof”

The page should communicate:
- This is the user’s travel identity.
- This person is verified or not verified.
- This person has a Trust Score.
- This person has collected stamps.
- This person has created postcards.
- This person may host events, join trips, or offer Rent a Buddy services.
- Other users can quickly decide whether they trust this traveler.

Do not make it look like a normal Instagram profile.
Do not make verification look like only a blue check.
Verification must look like an official passport stamp.

DATABASE / SUPABASE WIRING

Before adding new columns, inspect the current schema.

Do not blindly duplicate columns if profiles, profile_verifications, trust_scores, stamps, posts, trips, events, follows, and buddy tables already exist.

If missing, add only what is necessary.

Recommended profile verification columns if not present:

sql alter table public.profiles add column if not exists verification_status text not null default 'unverified'   check (verification_status in ('unverified', 'pending', 'verified', 'rejected', 'suspended')), add column if not exists verification_level text not null default 'none'   check (verification_level in ('none', 'basic_verified', 'trusted_traveler', 'host_verified', 'buddy_verified')), add column if not exists verified_since timestamptz, add column if not exists id_verified_at timestamptz, add column if not exists selfie_verified_at timestamptz, add column if not exists home_country_verified_at timestamptz, add column if not exists safety_flags_count integer not null default 0, add column if not exists host_verified_at timestamptz, add column if not exists buddy_verified_at timestamptz, add column if not exists cover_photo_url text; 

If verification data already lives in a dedicated verification table, do not move it. Instead create a safe API mapper.

PUBLIC-SAFE VIEW

Create a public-safe verification view or API mapper so sensitive identity data never goes to the client.

Example view if needed:

sql create or replace view public.public_profile_verification as select   id,   verification_status,   verification_level,   verified_since,   case     when verification_status = 'verified' and id_verified_at is not null     then true else false   end as id_verified,   case     when verification_status = 'verified' and selfie_verified_at is not null     then true else false   end as selfie_matched,   case     when verification_status = 'verified' and home_country_verified_at is not null     then true else false   end as home_country_verified,   case     when verification_status = 'verified' and safety_flags_count = 0     then true else false   end as no_safety_flags,   host_verified_at is not null as host_verified,   buddy_verified_at is not null as buddy_verified from public.profiles;

1. Navigate to an existing screen.
2. Open an existing sheet/modal.
3. Call a real backend action.
4. Show a clear “coming soon/admin disabled” state only if the feature truly is not available.
5. Be hidden until it can function.

Do not console.log only.
Do not silently fail.
