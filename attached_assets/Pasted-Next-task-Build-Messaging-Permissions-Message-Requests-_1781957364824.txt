Next task: Build Messaging Permissions + Message Requests for Travel Buddy.

Goal:
Create a safe messaging permission system that controls who can message whom, where message requests land, and how messages connect to friends/follows/trips/circles without creating privacy leaks.

Core product rule:
Messaging is its own permission layer.
Follow does not automatically grant messaging access unless product setting allows it.
Friendship can make messaging easier, but it should still respect user privacy settings.
Trip/circle membership can allow messaging only if explicitly supported by that context.

Relationship model:
- Follow = public discovery
- Friend = mutual social connection
- Circle = trusted privacy/live-map access
- Trip member = trip-specific travel access
- Messaging permission = communication access

Hard rule:
Do not let messaging unlock:
- private posts
- private Passport
- trip_only posts
- live location
- exact GPS
- circle access
- trip access

SECTION 1 — Messaging privacy settings

Add user messaging settings.

Suggested fields:
profiles or user_settings:
- message_privacy: everyone / followers / following / friends / trip_members / no_one
- allow_message_requests boolean
- allow_trip_member_messages boolean
- allow_circle_member_messages boolean
- message_language_preference if translation system exists later
- updated_at

Default recommended:
- message_privacy = friends
- allow_message_requests = true
- allow_trip_member_messages = true
- allow_circle_member_messages = true

Reason:
This keeps users safe while still allowing travel coordination.

SECTION 2 — Message permission resolver

Create a shared backend resolver:

canMessage(senderId, recipientId)

Inputs:
- sender
- recipient
- follow relationship
- friendship status
- trip membership overlap
- circle membership if relevant
- block status if blocking exists
- recipient messaging privacy settings
- existing accepted message thread if any

Output:
MessagePermissionVerdict:
- allowed: true/false
- requires_request: true/false
- reason
- relationship_context:
  - friend
  - follower
  - following
  - shared_trip
  - shared_circle
  - public_request
  - blocked
  - disabled
- safe_message

Rules:
- blocked users cannot message
- user cannot message themselves
- if recipient has message_privacy=no_one, block unless existing allowed system rule says otherwise
- if message_privacy=friends, friends can message directly
- if not allowed directly and allow_message_requests=true, create message request instead of direct inbox delivery
- if allow_message_requests=false, block
- shared trip members can message if allow_trip_member_messages=true
- shared circle members can message if allow_circle_member_messages=true

SECTION 3 — Message request model

Create message request layer.

Suggested table:
message_requests:
- id
- sender_id
- recipient_id
- status: pending / accepted / declined / blocked / cancelled
- preview_text
- created_at
- responded_at
- updated_at

Constraints:
- sender_id != recipient_id
- prevent duplicate pending requests
- only sender can cancel own request
- only recipient can accept/decline
- request does not create friendship
- request does not create follow
- request does not create circle/trip membership

When accepted:
- create or unlock message thread
- status accepted
- future messages can go to inbox unless recipient changes settings/block

When declined:
- no thread access
- optionally prevent duplicate request for cooldown period

SECTION 4 — Message thread access

Create or update message thread permission rules.

Message threads should only be accessible to participants.

Thread model if needed:

SECTION 5 — Request Inbox integration

Message requests should appear in the unified Request Inbox.

Request type:
- message_request

Inbox item:
“@user wants to message you”

Actions:
- Accept
- Decline
- Block if blocking exists

On accept:
- unlock/create thread
- allow sender and recipient to message

On decline:
- no thread access
- request marked declined

Pending count:
- include incoming pending message requests

SECTION 6 — Messaging UI behavior

When User A tries to message User B:

If direct messaging allowed:
- open chat thread

If message request required:
- show composer for first request message
- submit creates message_request
- show “Message request sent”

If messaging blocked:
- show clear message:
“This user isn’t accepting messages right now.”

If blocked:
- do not allow message
- do not reveal excessive block details if privacy-sensitive

Public profile/Passport:
- show Message button only when appropriate
- if message requires request, button can say “Message” but flow creates request
- owner does not see Message button on own profile

SECTION 7 — Trip and circle messaging

Shared trip:
- trip members can message each other if allow_trip_member_messages=true
- do not expose full trip details outside accepted membership
- if removed from trip, future messaging depends on thread state/settings

Shared circle:
- circle members can message if allow_circle_member_messages=true
- circle access must already be accepted
- circle membership is not created by messaging

Important:
Messaging a user does not invite them to a trip or circle.
Trip/circle invite remains separate.

SECTION 8 — Follow/friend behavior

Follow:
- does not automatically allow direct messaging unless recipient setting allows followers/everyone
- can allow message request if enabled

Friend:
- can allow direct messaging if message_privacy=friends
- friendship does not grant private Passport/live location/trip/circle access

SECTION 9 — Blocking compatibility

If blocking exists:
- blocked users cannot send message requests
- blocked users cannot send messages
- blocked users cannot see message button
- existing threads can be hidden/locked after block
- block should cancel pending message requests if product chooses

If blocking does not exist:
- leave clean TODO
- do not fake block behavior

SECTION 11 — Backend/API

Suggested endpoints:
- GET /api/me/message-settings
- PATCH /api/me/message-settings
- GET /api/users/:userId/message-permission
- POST /api/users/:userId/message-request
- POST /api/message-requests/:requestId/accept
- POST /api/message-requests/:requestId/decline
- POST /api/message-requests/:requestId/cancel
- GET /api/me/message-requests
- GET /api/me/threads
- GET /api/threads/:threadId/messages
- POST /api/threads/:threadId/messages
- POST /api/users/:userId/messages if direct create/open is supported

Security:
- resolve current user from auth token
- never trust client sender_id
- user cannot read threads they are not a member of
- user cannot accept another user’s message request
- user cannot create message request from someone else
- service-role key never exposed
