Travel Buddy — Complete User Profile Build Pass

We are working ONLY on the user profile system.

Do not rebuild the whole app.
Do not redesign unrelated screens.
Do not touch trips, events, meetups, RAB, notifications, discovery, admin dashboards, or web sharing unless the user profile system directly depends on them.
Do not add unrelated features.
Do not widen scope into public web Passport/share pages.
Do not fake success.
Do not leave dead buttons.
Do not leak blocked/private profile data.

Goal:
Finish the Travel Buddy user profile system completely for beta.

A complete profile system means:
1. Profile database fields exist and production is verified.
2. Backend profile routes are guarded and return correct safe data.
3. Profile edit saves every supported field.
4. Avatar upload works.
5. Cover photo upload works.
6. Own Passport/profile displays real data.
7. Public profile respects privacy and blocking.
8. Blocked/deleted/private users never leak data.
9. Profile actions work: edit, message, block, unblock, report.
10. Avatar taps route correctly from everywhere.
11. Stats, trust, badges, and verification are truthful.
12. No fake success, no dead buttons, no mock profile data.

Critical production context:
Recent production checks found:
- `profiles.cover_photo_url` is missing in production because migration 0087 was not applied.
- `profiles.role` is missing in production, even though admin guards may expect it.
- Cover photo upload/display will not work correctly until `cover_photo_url` exists.
- Admin bootstrap using `profiles.role = 'admin'` will fail unless the role source is fixed or verified elsewhere.

Start with schema/profile production readiness.

PHASE 1 — Profile schema and production verification

Audit the `profiles` table locally and in production.

Required fields to verify:
- id
- username / handle
- display_name
- bio
- avatar_url
- cover_photo_url
- home_city
- home_country
- default_language
- spoken_languages
- interests
- travel_style
- profile_visibility / privacy fields
- trust_score
- verified / verification_status
- role only if admin/profile logic depends on profiles.role
- created_at
- updated_at
- deleted/deactivated fields if present

Tasks:
1. Confirm `0087_profiles_cover_photo_url.sql` exists locally.
2. Confirm whether `profiles.cover_photo_url` exists in production.
3. If missing and production tooling allows, apply the safe SQL:
   `ALTER TABLE public.profiles ADD COLUMN IF NOT EXISTS cover_photo_url TEXT;`
4. Verify after apply with `information_schema.columns`.
5. Investigate `profiles.role`:
   - Search backend for `profiles.role`.
   - Search backend for `role = 'admin'`.
   - Search for `requireAdmin`.
   - Search migrations for role/admin columns.
   - Search for admin_users, user_roles, auth app_metadata, custom claims, or any other admin source.
6. Determine the actual intended admin role source:
   - If backend truly requires `profiles.role` and no migration creates it, prepare or apply the smallest safe migration:
     `ALTER TABLE public.profiles ADD COLUMN IF NOT EXISTS role TEXT NOT NULL DEFAULT 'user';`
     Add a safe check constraint only if existing code supports exact values.
   - If admin role comes from another source, do not add `profiles.role`; document and correct the runbook/docs if needed.
7. Do not run admin bootstrap until the role source is verified.

Deliverable:
- Profile schema status table.
- Exact SQL applied or required.
- Production verification query results.
- Admin role source conclusion.

Public profile states to handle:

2. Private profile.
3. I blocked this user.
4. This user blocked me.
5. Deleted/deactivated user.

Blocked profile behavior:
- If I blocked them:
  - show “Profile unavailable”
  - show unblock action

  - show “Profile unavailable”
  - no private data

- Do not expose avatar, cover, bio, posts, trip info, memories, or private fields for blocked profiles unless backend intentionally returns a safe stub.

Deleted/deactivated behavior:
- show “This profile is no longer available.”
- no crash if deleted user appears in threads/posts/notifications
- no private data leak
