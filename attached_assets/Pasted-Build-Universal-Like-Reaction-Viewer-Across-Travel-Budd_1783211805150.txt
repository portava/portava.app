Build Universal Like / Reaction Viewer Across Travel Buddy

Goal:
Allow users to tap any visible like/reaction count and see a privacy-safe, backend-backed list of users who liked/reacted to that content.

This should work across Travel Buddy surfaces where likes/reactions are enabled:
- Pulse posts
- Postcards
- video Postcards
- comments and replies
- Events
- Trips
- Hidden Gems
- Places / Locations
- Rent a Buddy profiles/listings where allowed
- Telegraph messages
- reviews / helpful votes where allowed

Core rule:
Anything with a visible like/reaction count can open a privacy-safe list of people who liked/reacted, only if the viewer has access to that content.

Do not create fake local like data. Do not create separate inconsistent like systems per feature. Use one reusable engagement viewer pattern and one backend access-checked service layer.

Keep these systems separate:
- Like/reaction = social engagement
- Save/bookmark = private or semi-private intent
- Join/request = membership intent
- Attending/member = event/trip access truth
- Booking = Rent a Buddy marketplace truth
- Telegraph reaction = thread-only engagement
- View = passive activity, not public
- Report = moderation/safety truth, never public

Do not expose:
- saved-by lists unless intentionally approved
- booked-by lists
- viewed-by lists
- reported-by lists
- private trip/event members through likes
- private Telegraph reactions outside the thread
- blocked users
- users who blocked the viewer
- deleted users
- banned/suspended users
- inaccessible/private users
- private exact locations
- emails, phone numbers, safety fields, verification internals, or private account settings

PHASE 2 — Universal Engagement Entity Contract

Goal:
Create one consistent model for fetching like/reaction lists by content type.

Suggested route:
GET /api/engagement/likes?targetType=&targetId=&reactionType=&cursor=&limit=&q=

Supported targetType values:
- post
- postcard
- video_postcard
- comment
- reply
- event
- trip
- place
- hidden_gem
- location
- buddy_profile
- telegraph_message
- review

Supported reactionType values:
- like
- love
- helpful
- fire
- laugh
- all

Rules:
- Use existing route style if the app already has engagement routes.
- If current backend uses separate tables, create a service layer that normalizes them.
- Do not force all engagement into one table if existing architecture is cleaner.
- Frontend should have one reusable viewer, even if backend internally reads from different tables.
- Return only viewer-visible reactions.
- Return public-safe user previews only.
- Use pagination.
- Default limit: 20.
- Validate targetType.
- Validate reactionType.
- Validate targetId.
- Validate q if list search is supported.
- Do not return every liker/reactor at once.
- Do not expose private fields.

Unified response shape:
- targetType
- targetId
- reactionType
- viewerVisibleCount
- totalCount only if privacy-safe and already used
- users:
  - id
  - avatarUrl
  - fallbackInitials
  - displayName
  - username/handle
  - basic location only if allowed
  - verified/trust badge if public
  - followState
  - mutualIndicator if useful
- nextCursor
- hasMore

Validation:
- One reusable viewer can fetch like lists for different content types.
- Backend validates targetType and reactionType.
- Backend validates viewer access per target type.
- Response shape is consistent.
- Private fields are not returned.

PHASE 3 — Universal Access Guard

Goal:
Every engagement list request must pass a target-specific backend access guard before returning any users.

Access checks:
- post access
- Postcard access
- video Postcard access
- comment access
- reply access
- event access
- trip access
- place/gem visibility
- Rent a Buddy profile/listing visibility
- Telegraph thread membership
- review parent access
- parent-chain access where applicable

Rules:
- Access guard runs before returning any liker/reactor user.
- Access guard runs on the backend.
- Frontend hiding is not enough.
- Check the target itself and its parent chain.
- If any parent is private, inaccessible, deleted, hidden, rejected, or moderation-suppressed, engagement list must be blocked.
- Do not rely only on the direct target id.
- Unauthorized requests should return a safe error:
  - “This content isn’t available.”
  - or “Likes are private.”

Parent-chain examples:
- comment likes inherit comment + post access.
- reply likes inherit reply + comment + post access.
- review helpful votes inherit review + place/event/buddy access.
- Telegraph message reactions inherit thread membership.
- event-linked Postcard likes inherit event access if event-linked and restricted.
- trip-linked Postcard likes inherit trip access if trip-only.
- place-linked private Hidden Gem media inherits gem/place visibility.

Validation:
- Unauthorized viewer cannot fetch likes by guessing targetType/targetId.
- Private trip Postcard likes do not leak.
- Private event Postcard likes do not leak.
- Hidden parent post blocks comment like lists.
- Telegraph reactions cannot be fetched outside the thread.
- Removed Telegraph participant cannot fetch reactions after removal if app policy blocks history.
- Private trip/event likes cannot be fetched by non-members.
- Hidden content engagement is protected.

PHASE 38 — Final Universal Engagement Lock Rule

Lock the product meanings:

- Like/reaction = social engagement.
- Save/bookmark = private or semi-private intent.
- Join/request = membership intent.
- Attending/member = event/trip access truth.
- Booking = Rent a Buddy marketplace truth.
- Telegraph reaction = thread-only engagement.
- View = passive activity and should not be exposed as a liker list.
- Report = moderation/safety truth and never public.
- Safety feedback = private/moderation-facing, not social engagement.

Rules:
- Do not mix these concepts.
- Do not expose saved-by, booked-by, joined-by, attended-by, viewed-by, or reported-by as like lists.
- Do not expose private trip/event members through likes.
- Do not expose private Telegraph reactions outside the thread.
- Each system must use its own backend truth and privacy policy.
- Engagement viewer must only show viewer-visible users who liked/reacted.
- Backend access checks must run before returning engagement users.
