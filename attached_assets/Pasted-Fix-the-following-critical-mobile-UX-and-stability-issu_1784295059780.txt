## 1. KEYBOARD / TEXT INPUT POPUPS BLOCK THE SCREEN

Problem:

Whenever a page, modal, bottom sheet, composer, popup, or form opens the keyboard for typing, the keyboard covers the active input and blocks the user from seeing what they are typing.

This must be fixed globally, not one screen at a time.

Audit every screen containing:

- TextInput
- Search inputs
- Comment inputs
- Memory composer
- Postcard composer
- Profile editing
- Telegraph messaging
- Event creation
- Trip creation
- Rent a Buddy forms
- Reports
- Reviews
- Captions
- Bio fields
- Location search
- Any modal or bottom-sheet input

Implement a consistent keyboard-safe architecture.

Requirements:

- The focused TextInput must remain visible above the keyboard.
- The screen must automatically adjust when the keyboard opens.
- Users must be able to scroll focused fields into view.
- Bottom-sheet inputs must resize or move correctly.
- Modal inputs must remain visible.
- The keyboard must never cover submit/post/save buttons when those buttons are needed.
- Tapping outside the input should dismiss the keyboard where appropriate.
- Do not create excessive empty space after the keyboard closes.
- Preserve safe-area insets.
- Preserve Android and iOS behavior separately where needed.
- Avoid nested-scroll conflicts.

Use the appropriate existing Expo / React Native architecture, such as KeyboardAvoidingView, keyboard-aware scrolling, bottom-sheet keyboard behavior, or the project's existing equivalent.

Do not blindly wrap every page with multiple competing keyboard handlers.

Create one reusable keyboard-safe pattern/component where practical and migrate affected screens to it.

Test:

1. Focus first field.
2. Focus last field.
3. Scroll while keyboard is open.
4. Open and close keyboard repeatedly.
5. Test multiline inputs.
6. Test inside modal.
7. Test inside bottom sheet.
8. Test iOS.
9. Test Android.

The user must always be able to see the text currently being entered.

# 2. MEMORY + POSTCARD LOCATION SEARCH DOES NOT HELP USERS FIND A LOCATION

Problem:

When posting a Memory or Postcard, the location system does not properly assist the user while typing.

The location field must behave like a real location autocomplete/search field.

Audit the complete flow:

User types location
→ search/debounce
→ location provider
→ results
→ result selection
→ normalized location object
→ coordinates
→ display name
→ post draft
→ database save
→ post display
→ map/location features

Fix both:

- Create Memory
- Create Postcard

Do not maintain two conflicting location implementations.

Use the app's shared/global location system where one already exists.

Required UX:

When the user begins typing:

- Show suggested matching locations.
- Search cities.
- Search neighborhoods.
- Search landmarks.
- Search venues/POIs where supported.
- Search addresses where supported.
- Show useful labels such as city + country or venue + city.
- Results should update as the user types.
- Add debounce to prevent excessive requests.
- Cancel or ignore stale requests.
- Show loading state.
- Show empty state.
- Show recoverable error state.
- Keyboard must not cover the results.

When a location is selected, persist a structured object rather than only raw text.

Store/use available fields such as:

- displayName
- name
- address
- city
- region/state
- country
- countryCode
- latitude
- longitude
- providerPlaceId if applicable
- location type/category if applicable

Respect the existing database schema. If schema expansion is genuinely required, create a migration rather than breaking current records.

Do not overwrite intentional privacy behavior.

If the app intentionally delays exact geolocation publishing until a user leaves an area, preserve that behavior.

The composer should still be able to show the user the selected location while ensuring published location data follows the existing privacy rules.

Also audit:

- location permissions
- foreground location
- GPS fallback
- manual location selection
- current-location button
- autocomplete service configuration
- API/environment variables
- web versus native differences

If the external autocomplete provider is unavailable, the field must fail gracefully and still permit an appropriate manual location value instead of appearing broken.

- media aspect ratios
- image loading
- video autoplay

- animations

- bottom navigation
- floating menus
- location updates

- impression tracking

There should be one primary vertical scrolling owner for the Pulse feed.
