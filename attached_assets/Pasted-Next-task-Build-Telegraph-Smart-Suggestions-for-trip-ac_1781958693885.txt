Next task: Build Telegraph Smart Suggestions for trip/activity recommendations.

Goal:
Add an in-app recommendation system called Telegraph that recommends activities, places, meetups, and plan ideas based on the user’s trip, profile, interests, availability, location settings, and social context.

Core product rule:
Telegraph should help users discover what to do next and make it easy to add suggestions into their trip plan.

Telegraph should recommend:
- activities
- restaurants
- nightlife
- beaches
- attractions
- hidden gems
- meetups
- trip plan ideas
- nearby public events if data exists
- public group trips/activities if available

Telegraph should not expose:
- private trips
- private posts
- trip_only content to non-members
- live location
- exact GPS
- private availability
- circle data
- private Passport data

SECTION 1 — Telegraph definition

Telegraph is the recommendation/message intelligence layer inside Travel Buddy.

It can appear in:
- trip detail
- trip plan
- discovery map
- Pulse
- Passport
- trip/circle chat
- home screen
- request inbox later

Telegraph should feel like:
“Here are smart things to do based on your trip and preferences.”

Not:
“Random ads or generic recommendations.”

SECTION 2 — Recommendation inputs

Telegraph should use available context:

User profile:
- interests
- travel style
- languages
- home base if useful
- public Passport signals
- saved places
- past postcard categories

Trip context:
- destination
- trip dates
- trip members
- trip plan items
- unscheduled time
- current itinerary gaps
- trip visibility
- trip preferences if available

Availability:
- user availability
- trip member availability overlap
- meetup times
- quick status like free tonight

Social context:
- followed travelers’ public recommendations
- friends’ public postcards if allowed
- trip members’ public/shared preferences
- group chat meetup ideas

Location context:
- destination city
- current city if user allows
- nearby discovery places
- safe approximate location
- never exact GPS unless user explicitly allows and it stays private/safe

Content context:
- public posts
- public postcards
- public places
- public activities
- verified/trusted traveler ratings
- saved items

SECTION 3 — Recommendation types

Create recommendation types:

1. Activity
Example:
“Sunset beach walk near Mactan”

2. Food/restaurant
Example:
“Seafood dinner near your hotel area”

3. Nightlife
Example:
“Hip-hop lounge in Ximending tonight”

4. Attraction
Example:
“Temple visit before dinner”

5. Meetup
Example:
“Two trip members are free Friday night — suggest dinner meetup”

6. Plan gap filler
Example:
“You have Saturday afternoon open — add a beach club or city walk”

7. Social recommendation
Example:
“Three travelers saved this place”

8. Passport-inspired recommendation
Example:
“You’ve posted a lot of nightlife memories — here are nightlife picks near this trip”

9. Weather/time-aware recommendation later
Example:
“Rain likely tonight — indoor lounge instead of beach plan”

SECTION 4 — Recommendation object

Create:
TelegraphRecommendation

Fields:
- id
- user_id
- trip_id nullable
- source_type: place / activity / meetup / post / postcard / plan_gap / social / manual
- source_id nullable
- title
- description
- category
- location_name nullable
- city nullable
- country nullable
- approximate_lat nullable
- approximate_lng nullable
- reason
- confidence
- relevance_score
- privacy_tier: public / trip / private
- suggested_time nullable
- suggested_day nullable
- action_type: add_to_plan / save / create_meetup / view_place / invite
- created_at
- expires_at nullable
- dismissed_at nullable
- acted_on_at nullable

Important:
Recommendation object should be display-safe.
Do not include private fields in public response.

SECTION 5 — Telegraph engine

Create:
TelegraphRecommendationEngine

Inputs:
- current user
- trip context if present
- profile/interests
- plan gaps
- availability
- public discovery data
- public social data
- privacy rules

Output:
- ranked recommendations
- reason for each recommendation
- suggested action
- privacy-safe payload

Scoring factors:
- interest match
- trip destination match
- time fit
- availability fit
- plan gap fit
- social proof
- distance/location fit if safe
- category diversity
- freshness
- weather/news/event fit later

SECTION 6 — Recommendation rules

Telegraph should:
- recommend a mix of categories
- avoid repeating items already in plan
- avoid suggesting dismissed items again too soon
- prioritize suggestions that fit open trip windows
- recommend meetups when members’ availability overlaps
- recommend nearby places only with safe location rules
- explain why recommendation appears

Telegraph should not:
- suggest private places from other users
- expose exact user locations
- use trip_only data outside trip members
- use private Passport data for public recommendation
- recommend impossible timing
- spam too many suggestions
- act without user confirmation

SECTION 9 — Add-to-Plan integration

Telegraph recommendations must connect to Trip Plan Builder.

Action:
Add to Plan

Flow:
- tap Add to Plan
- choose trip if not already inside trip
- choose day/time optional
- confirm
- create trip_plan_item with source_type recommendation/place/activity/meetup
- mark recommendation acted_on_at
- show toast

Rules:
- do not duplicate existing plan item
- if source already in trip plan, show “Already in plan”
- do not add to trip if user is not accepted trip member
- respect trip plan permissions

SECTION 10 — Meetup integration

Telegraph can suggest meetups when:
- trip members have overlapping availability
- circle members are free
- chat has planning intent
- open trip gap exists

Flow:
- Telegraph suggestion: “Create meetup”
- prefill title/time/location if available
- user confirms
- create meetup
- optionally add to trip plan
- post compact card to trip/circle chat

Rules:
- never auto-create meetup without confirmation
- invited users must RSVP
- no private availability leak

SECTION 11 — Privacy

Telegraph must use a privacy resolver before returning suggestions.

Privacy rules:
- public suggestions can use public data only
- trip suggestions can use trip data only for accepted members
- circle suggestions can use circle data only for accepted members
- availability suggestions only use availability shared with that viewer
- public profile/passport data can influence only if visible
- exact GPS never exposed
- private notes never exposed
- private trip details never exposed to non-members

SECTION 12 — API endpoints

Suggested endpoints:
- GET /api/telegraph/recommendations
- GET /api/trips/:tripId/telegraph/recommendations
- POST /api/telegraph/recommendations/:id/dismiss
- POST /api/telegraph/recommendations/:id/add-to-plan
- POST /api/telegraph/recommendations/:id/create-meetup
- POST /api/telegraph/refresh

Optional:
- GET /api/telegraph/recommendations?surface=trip_plan
- GET /api/telegraph/recommendations?surface=chat
- GET /api/telegraph/recommendations?surface=discovery

Security:
- resolve user from auth token
- never trust client user_id
- verify trip membership before trip recommendations
- verify circle membership before circle recommendations
- never expose service-role key

SECTION 13 — Reason text

Each recommendation should explain itself clearly.

Reason examples:
- “Matches your nightlife interests.”
- “Your Friday night is open.”
- “This is near your planned dinner.”
- “Two trip members are free around this time.”
- “You saved similar beach spots.”
- “Popular with travelers in this area.”
- “Fits your trip plan gap on Saturday afternoon.”

Avoid creepy reasons:
- do not say exact hidden location
- do not expose private user data
- do not say “because we tracked you”
- do not reveal another user’s private availability

SECTION 14 — Dismiss/save behavior

Users can:
- dismiss recommendation
- save recommendation
- add to plan
- create meetup
- view details

Dismiss:
- hides recommendation
- prevents immediate repeat
- logs feedback

Save:
- adds to saved items if save system exists
- otherwise leave TODO

Feedback fields:
- dismissed_at
- dismiss_reason optional
- acted_on_at
- action_taken

SECTION 15 — Diversity and anti-spam

Telegraph should not flood users.

Rules:
- max 5–8 recommendations per surface
- mix categories
- do not show the same item repeatedly
- do not show dismissed items immediately
- do not recommend already-planned items
- prioritize useful timing/context over generic lists
