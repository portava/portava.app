Build Backend and Database Support for Video Postcards

Goal:
Allow users to upload videos as Postcards. Postcards can be photo or video posts connected to Pulse, Passport, trips, events, places, hidden gems, hashtags, and Discovery search.

Do this backend/database first. Do not focus on the frontend upload UI yet except where needed to confirm integration points.

Core rule:
Do not create a separate “videos” system if the app already has posts/postcards. Extend the existing Postcards/Pulse media system so photos and videos share one truth.

First inspect the current backend/database before changing anything.

Find:
- existing posts table
- existing postcards table, if any
- existing media table, if any
- existing storage bucket usage
- existing upload endpoints
- existing Pulse feed endpoints
- existing Passport media/profile post endpoints
- existing trip/event/place attachment logic
- existing hashtag extraction logic
- existing moderation/reporting fields
- existing privacy/visibility fields

Confirm:
- whether photos already upload through Supabase Storage or another provider
- whether media is stored as a URL on posts or in a separate media table
- whether multiple media items per post are supported
- whether videos are already partially supported but not wired
- whether storage policies already exist

Deliverable:
Before patching, briefly report the existing truth:
- current tables used
- current media fields
- current upload path
- current gaps blocking video uploads

PHASE 2 — Database Model

Goal:
Support photo and video media cleanly.

Preferred structure:
Use a dedicated postcard_media or post_media table if one does not already exist.

Suggested table:
postcard_media

Fields:
- id uuid primary key
- postcard_id uuid nullable if the app uses postcards
- post_id uuid nullable if the app uses posts
- user_id uuid not null
- media_type text not null
  - allowed values: image, video
- storage_bucket text not null
- storage_path text not null
- public_url text nullable
- thumbnail_storage_path text nullable
- thumbnail_url text nullable
- mime_type text nullable
- file_size_bytes bigint nullable
- duration_seconds numeric nullable
- width integer nullable
- height integer nullable
- processing_status text not null default 'ready'
  - allowed values: pending, processing, ready, failed
- moderation_status text not null default 'pending'
  - allowed values: pending, approved, rejected, flagged
- sort_order integer not null default 0
- created_at timestamptz not null default now()
- updated_at timestamptz not null default now()

Rules:
- If the app already has post_media, extend it instead of creating duplicate postcard_media.
- If the app already stores media directly on posts, migrate toward a media table only if safe.
- Support one or multiple media items per postcard if existing product direction allows carousels.
- For now, allow at least one video per postcard.

Constraints:
- media_type must be image or video.
- processing_status must be valid.
- moderation_status must be valid.
- either post_id or postcard_id must be present depending on the app’s current model.
- user_id must match the owning post/postcard user.

Indexes:
- index on user_id
- index on post_id
- index on postcard_id
- index on media_type
- index on processing_status
- index on moderation_status
- index on created_at
- optional composite index on user_id, created_at desc

Validation:
- Migration runs cleanly.
- Existing photo posts still work.
- Existing Pulse feed does not break.
- Existing Passport posts do not break.

If existing posts/postcards table lacks these fields, add safe additive fields:

Suggested fields:

- media_count integer not null default 0
- has_video boolean not null default false
- visibility text existing or new if needed
  - public, followers, private, trip, event
- location_id uuid nullable if places exist
- trip_id uuid nullable
- event_id uuid nullable
- city text nullable
- country text nullable
- caption text nullable if not already present

Rules:

- Do not rename existing fields unless required.
- Keep migration additive and backward compatible.
- Backfill existing posts:
  - image posts should become primary_media_type = image
  - no media posts should become primary_media_type = none
  - media_count should reflect existing media if possible

Validation:
- Existing post reads still work.
- Existing feed serializers still return expected fields.
- Old posts remain visible.

PHASE 4 — Storage Bucket and File Rules

Goal:
Support safe video storage.

Create or extend storage bucket:
- preferred bucket name: postcards
- if existing media bucket exists, use it instead
- paths should be user-scoped

Suggested storage paths:
- postcards/{user_id}/{postcard_id}/original/{media_id}.{ext}
- postcards/{user_id}/{postcard_id}/thumb/{media_id}.jpg

Allowed video MIME types:
- video/mp4
- video/quicktime
- video/webm if supported by app/player

Allowed image MIME types:
- image/jpeg
- image/png
- image/webp

Recommended limits:
- image max size: keep existing limit if present
- video max size: start with 100MB or lower if mobile/storage constraints require
- video max duration: start with 60 seconds for Postcards
- later, if desired, allow shorter 10-second quick postcards for profile highlights

Rules:
- Validate MIME type server-side.
- Validate file size server-side.
- Validate extension server-side.
- Do not trust client-provided MIME alone if file inspection exists.
- Do not allow executable or unknown file types.
- Store only public-safe URLs or signed URL paths based on visibility.
- Private/followers-only media should not be permanently public if app privacy requires signed URLs.

Validation:
- Video files can be uploaded.
- Invalid file types are rejected.
- Oversized files are rejected.
- User cannot upload into another user’s path.

PHASE 5 — Backend Upload Flow

Goal:
Create a reliable upload flow for video Postcards.

Preferred flow:
1. Authenticated user creates a Postcard/post draft.
2. Backend creates media record with processing_status = pending.
3. Backend returns signed upload URL or upload instructions.
4. Client uploads file to storage.
5. Client/backend confirms upload completion.
6. Backend validates metadata.
7. Backend updates media record.
8. Backend updates parent post/postcard media_count, has_video, and primary_media_type.
9. Postcard becomes visible only when media is ready and privacy rules allow it.

Suggested endpoints:
- POST /api/postcards
  - create postcard/post with caption, visibility, location/trip/event links
- POST /api/postcards/:id/media/upload-url
  - create media row and return signed upload URL
- POST /api/postcards/:id/media/:mediaId/complete
  - mark uploaded, store metadata, set processing_status
- GET /api/postcards/:id
  - return postcard with media
- DELETE /api/postcards/:id/media/:mediaId
  - remove media if owner

Alternative:
If app already has upload endpoints, extend those endpoints instead of creating duplicates.

Validation:
- User can create postcard draft.
- User can request video upload URL.
- User can complete upload.
- Media appears on the postcard.
- Parent postcard fields update correctly.
- Unauthorized user cannot attach media to someone else’s postcard.

PHASE 6 — Video Metadata and Thumbnail Support

Goal:
Store enough video information for frontend playback.

Metadata to capture:
- duration_seconds
- width
- height
- mime_type
- file_size_bytes
- thumbnail_url or thumbnail_storage_path
- processing_status

Thumbnail:
- If server-side thumbnail generation already exists, use it.
- If not, allow client to upload a thumbnail frame as part of the complete step.
- Store thumbnail separately from the original video.
- If thumbnail is missing, frontend can use a default video placeholder.

Processing:
- If no transcoding pipeline exists, do not pretend videos are processed.
- Set processing_status = ready after upload validation only.
- Leave clean TODO for future transcoding/compression if needed.
- If processing fails, set processing_status = failed and hide from public feed.

Validation:
- Video media returns duration and dimensions if available.
- Thumbnail appears when present.
- Missing thumbnail does not break API.
- Failed media is not shown in public feeds.

PHASE 8 — Privacy and Access Control

Goal:
Video Postcards must follow the same privacy rules as posts.

Enforce:
- public
- followers-only, if supported
- private
- trip-only
- event-only
- circle/group-only, if supported
- blocked users
- users who blocked viewer
- muted/hidden users if app rules require it
- deleted/banned/suspended accounts hidden
- moderation-hidden media hidden
- age-restricted content hidden where applicable

Backend rules:
- Viewer access must be checked before returning media.
- Storage URLs must not bypass app privacy.
- Signed URLs should expire for private media.
- Public URLs are okay only for public media if app allows public storage.

Validation:
- Unauthorized viewer cannot fetch private video metadata.
- Unauthorized viewer cannot get private signed URL.
- Blocked viewer cannot see media.
- Deleted/banned/suspended author media does not appear.

- Update hashtag usage count if supported.
- Store city/country/location if user attaches location.
- Link trip_id/event_id/place_id if provided.
- Add to Pulse/Discovery only if visibility allows.

Validation:

PHASE 11 — Deletion and Cleanup

Goal:
Deleting a Postcard or media should clean up safely.

Rules:
- User can delete their own video Postcard.
- Admin can remove media if admin system supports it.
- Deleting media should:
  - remove or mark media row deleted depending on current app convention
  - remove storage object where safe
  - update parent media_count
  - update parent primary_media_type and has_video
- If deleting the only media item, post should either become text-only or be deleted based on app rules.
- Do not orphan storage files if cleanup is supported.
- If physical delete is risky, soft-delete metadata and schedule cleanup later.

Validation:
- User can delete own video.
- User cannot delete another user’s video.
- Parent post counts update.
- Feed no longer shows deleted media.

PHASE 12 — Security and Abuse Protection

Goal:
Prevent misuse of video uploads.

Add:
- auth required for upload endpoints
- ownership checks
- rate limit upload URL creation if app has rate limiter
- file size validation
- MIME validation
- path validation
- max media count per postcard
- max video duration metadata check where possible
- storage policy limiting users to their own folder/path
- no empty-query/list-all media endpoint

Validation:
- Unauthenticated upload fails.
- Upload to another user path fails.
- Oversized video fails.
- Unsupported MIME fails.
- Too many media items fails.

- Public media read can be allowed only if the app’s privacy model supports it.
