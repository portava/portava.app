Next task: Build Follow UI on Passport/Profile.

Goal:
Add the user-facing Follow experience now that the follow backend exists.

This task should connect the existing follow backend to the Passport/Profile UI.

Core product rule:
Follow = public social discovery only.
Follow must not grant private posts, trip_only posts, circle membership, trip access, or live-map visibility.

Do not connect follows to:
- circle_memberships
- trip_members
- live location
- private Passport access
- trip_only content access

SECTION 1 — UI surfaces

Add follow UI to:

1. Public Passport page
- show Follow button when viewing another user
- show Following state if already followed
- allow Unfollow
- show followers/following counts if backend supports them

2. Profile header
- owner does not see Follow button on own Passport
- public viewer sees Follow/Following button
- blocked users should not see/interact if blocking exists

3. Optional Profile card usage
If traveler cards exist in Pulse/Discovery/Search:
- show small Follow button or status if easy
- do not overbuild this pass

SECTION 2 — Button states

Follow button states:
- Follow
- Following
- Loading
- Error
- Unfollow confirmation if desired

Rules:
- optimistic update allowed only if rollback works on failure
- duplicate follow should not duplicate count
- if API returns already-following, UI should show Following
- if unfollow succeeds, UI returns to Follow
- disabled while request is pending

SECTION 3 — Counts

Show compact counts:
- Followers
- Following

Rules:
- counts update after follow/unfollow
- no NaN/null/undefined
- counts should not become negative
- if endpoint unavailable, hide counts or show fallback cleanly

SECTION 4 — API integration

Use existing endpoints:

- POST /api/users/:userId/follow
- DELETE /api/users/:userId/follow
- GET /api/users/:userId/follow-status
- GET /api/me/following
- GET /api/me/followers

If counts endpoint exists:
- use it

If counts endpoint does not exist:
- add lightweight count support or return counts from public Passport payload if safe

Do not expose private data in followers/following responses.

SECTION 5 — Privacy rules

Follow should only affect:
- public content discovery
- public Passport/profile relationship display
- optional Following feed later

Follow must not unlock:
- private Passport
- private posts
- trip_only posts
- trip member data
- circle member data
- live location
- exact GPS
- direct messaging unless product already allows it separately

SECTION 6 — Public Passport behavior

When User A views User B’s public Passport:
- if not following: show Follow
- if following: show Following
- if owner: hide Follow button
- if Passport private: public profile can still show limited private state, but no private postcards
- follow state should still work if profile is visible enough to follow

SECTION 7 — Optional Following feed filter

Add only if simple and backend already supports it.

Pulse filter:
- For You / Following / Nearby if existing
- Following shows public posts from followed users only

Rules:
- Following filter must include public posts only
- private/trip_only posts remain protected
- if no followed users: show empty state

Empty state:
“Follow travelers to see their public posts here.”

If this requires too much backend work, leave as follow-up.

SECTION 8 — Mobile layout

Mobile requirements:
- Follow button fits in Passport header
- no horizontal overflow
- counts wrap cleanly
- loading/error states clean
- button is easy to tap
- works at 390px and 430px

Desktop:
- preserve existing Passport layout
- button should align cleanly in header/action area
