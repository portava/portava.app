Run a full SQL/backend database audit for Travel Buddy.

Goal:
Audit the current backend database layer and produce an exact report of what SQL/database pieces are missing, incomplete, unused, mismatched, or required to make the app’s backend fully support the UI/features already built or planned.

Do not blindly create migrations. Do not run destructive SQL. Do not alter production data. First inspect everything, compare schema vs backend services vs frontend usage, then produce a precise SQL action plan. Only apply tiny safe migrations if explicitly low-risk and required to fix a confirmed compile/runtime blocker.

Primary objective:
Find:
- Missing tables
- Missing columns
- Missing indexes
- Missing foreign keys
- Missing unique constraints
- Missing RLS policies if Supabase RLS is used
- Missing enums
- Missing join tables
- Missing storage buckets/policies
- Missing triggers/functions
- Missing seed data
- Missing migration entries
- Tables/columns used by code but absent from SQL
- SQL objects that exist but no code uses
- Backend routes/services expecting fields that are not in schema
- UI features that require database support but do not have it yet
- SQL commands/migrations needed to fix each gap

Important rules:
- Be brutally honest.
- Do not assume a database object exists because TypeScript types mention it.
- Do not assume a feature is persisted unless schema, backend route, and service usage confirm it.
- Do not generate destructive SQL such as DROP TABLE, TRUNCATE, or destructive column changes.
- Do not rename columns without a migration/backfill strategy.
- Do not weaken privacy/security rules.
- Do not fake database support by adding frontend-only local storage.
- Do not modify standalone directly unless the project workflow requires sync from canonical source.
- Prefer producing an exact migration plan over applying large schema changes in this audit.

5. SQL command output
For every recommended migration, provide:
- Migration filename suggestion, e.g. 0094_add_trip_saved_ideas.sql
- Purpose
- Dependencies
- Safe SQL draft
- Backfill needs
- Rollback notes
- Test plan

SQL draft rules:
- Use CREATE TABLE IF NOT EXISTS where safe.
- Use ALTER TABLE ... ADD COLUMN IF NOT EXISTS where safe.
- Add indexes with CREATE INDEX IF NOT EXISTS.
- Add unique constraints carefully.
- Do not include destructive drops.
- Do not include broad permissive RLS policies.
- If RLS is used, propose conservative owner/member policies.
- If a policy cannot be safely inferred, mark it “needs owner decision” instead of guessing.
- Include comments explaining each migration.
- Include timestamps/created_at/updated_at where appropriate.
- Include updated_at trigger/function only if the project already uses that pattern; otherwise report the missing pattern.
