Fix the Passport/Profile editing system end-to-end without rebuilding unrelated systems.

This is an audit-and-fix pass, not a rebuild. The current issue is that users cannot properly edit and save their Passport/Profile page. Saving still says the user “cannot select a username,” which likely means username/handle validation got mixed up with real name/display name, stale form state, backend error mapping, or profile completion logic.

The profile should be fully editable and savable after this pass. Fix the real root cause, not just the visible error message.

Current bugs:
- User cannot properly edit and save their profile page.
- Saving still says the user “cannot select a username.”
- Username/handle appears to be mixed up with real/display name.
- Profile completion appears stuck or incomplete.
- Passport/Profile menu button looks outdated.
- User cannot change the back-page/header/cover photo directly from Passport.
- Passport profile photo camera button should ask whether the user wants to change display photo or add/change a highlight.

Core safety rules:
- Do not rebuild the Passport page from scratch.
- Do not create a duplicate profile system.
- Do not break onboarding.
- Do not break public profile viewing.
- Do not break Trip Crew, Telegraph, Pulse, Discovery, profile links, or user cards.
- Do not change database schema unless absolutely required.
- If schema is required, add a safe migration and update database types.
- Keep changes small, traceable, and cohesive.
- Reuse existing storage/upload/profile helpers where possible.
- Run relevant tests and type checks before reporting completion.

2. Fix username vs real/display name confusion

Username/handle must be completely separate from display name/real name.

Rules:
- Username/handle saves to the correct username/handle field.
- Display name/real name saves to the correct display name field.
- Editing display name must not trigger username validation.
- Editing bio, location, languages, interests, avatar, cover photo, or highlights must not trigger username validation.
- User should never see “cannot select a username” when only editing normal profile info.
- If username is required for profile completion, show a clear username field and clear validation message.
- If username is already set, allow the rest of the profile to save without asking for username again.
- Username uniqueness checks should only run when username is changed or when a brand-new user is required to choose one.
- Existing username should be allowed to save unchanged.
- Username uniqueness must ignore the current user’s own username.
- Username uniqueness should be case-insensitive if the app treats usernames case-insensitively.

Normalize username safely:
- trim spaces
- remove leading @
- lowercase
- allow only the app’s accepted username characters
- store raw username without @
- display visually as @username where appropriate

Use one consistent user-facing term:
- Prefer “Username” or “Handle,” not both unless the UI explains it.
- Prefer “Display name” instead of confusing “real name,” unless the app intentionally requires legal names.

3. Fix duplicate/stale username checks

Search for every place the app checks username availability.

Remove or bypass stale checks that fire during normal profile saves.

The username check should not run just because a save button was pressed. It should run only when username changed or when username is truly required and missing.

- Empty optional fields should be handled intentionally.
- If one optional field fails, do not block unrelated fields unless backend/database requires it.
- Profile completion status should update correctly after save.
