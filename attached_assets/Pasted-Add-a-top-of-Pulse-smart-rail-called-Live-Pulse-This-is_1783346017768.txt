Add a top-of-Pulse smart rail called “Live Pulse.”

This is a core Travel Buddy beta feature, not a decorative banner. It should turn the Pulse page into a real-time action center showing what is happening now, what is starting soon, what needs the user’s attention, and what they can join, save, request, message, or manage.

Do not rebuild Pulse. Do not create a separate fake event banner. Do not duplicate recommendation logic. Do not use placeholder/demo data. Live Pulse must use real app data and the same shared truth layer used by Events, Trips, Circles, Rent a Buddy, Discovery, Compass, Find Your Circle, Trip Crew, Notifications, Availability, Privacy, and Safety.

Core requirement:

Every Live Pulse card must either:

1. Open the correct real object.
2. Perform the correct real action.
3. Be hidden or disabled with an honest reason.

No dead buttons. No fake success. No stale cards. No private data leaks.

---

# 1. Feature name and placement

Add a smart rail at the top of the Pulse page.

Name:

Live Pulse

Placement:

- At the top of Pulse, above the main feed.
- Mobile-first.
- Horizontally scrollable.
- Collapsible.
- Not too tall.
- Should not push the feed too far down.
- Should have a clean loading state, empty state, and error/retry state.

The rail should feel like:

“What is happening around me / my trip / my city right now?”

# 3. Supported Live Pulse item types

Live Pulse should support these real item types where implemented:

## Events

- Starting soon events
- Ongoing events
- Events ending soon
- Tonight’s events
- Tomorrow’s events
- Upcoming events
- Joined events
- Saved events
- Hosted events
- Invite-only events where user can request
- Full events where waitlist exists

## Trips

- Active trips
- Upcoming trips
- Trips starting soon
- Joined trips
- Saved trips
- Hosted trips
- Trips with crew activity
- Trips with pending join requests
- Trips tied to current city or selected trip city

## Circles

- Circles gathering now
- Circles tied to user’s trip
- Circles tied to current city
- Circles with active members
- Circles the user joined
- Circles with pending requests
- Invite-only circles where user can request

## Rent a Buddy

- Available buddies today
- Buddies available near selected city/trip city
- Saved buddies
- Buddy requests sent by user
- Buddy requests received by buddy
- Upcoming buddy bookings/requests
- Buddy profiles needing action
- Buddy availability prompts

If payments are not fully wired, do not show fake payment/deposit actions. Use request-only or hide payment actions.

## Hidden Gems

- Relevant nearby gems
- Gems tied to trip city
- Gems popular with similar travelers
- Gems saved by the user
- Gems with directions action if map/location is available

## Safety / Safe Return

- Active Safe Return check-in
- Check-in due soon
- Missed check-in requiring action
- Trip safety reminder
- Safety card must be honest and must not claim emergency dispatch unless actually wired

## Compass-backed picks

- Compass picks backed by real app objects only
- No invented events
- No invented people
- No invented buddies
- No fake places
- No unsupported claims

## Host and management cards

Live Pulse should also show user-owned responsibilities:

- Join requests waiting for host
- Event/trip/circle starting soon that user hosts
- Message attendees prompt
- Buddy request received
- Buddy request pending
- Circle member request
- Trip Crew activity
- Event update requiring attention

# 4. Required card structure

Each Live Pulse card should include:

- Status badge
- Object type
- Title
- Time or distance
- City/location label
- People count where relevant
- Reason label
- User relationship state
- Primary action
- Secondary action where useful

Example structure:

txt Starting Soon Rooftop Drinks Starts in 24m · Shibuya · 8 going Because you like nightlife Join · View 

Another example:

txt Action Needed 2 join requests Tokyo Food Crawl starts tonight Review · Manage 

Another example:

txt Buddy Available Mika · Local nightlife buddy Available today · Bangkok Request · Message 

---

# 5. Status labels and time rules

Use exact status logic.

txt Starting Soon = starts within 60 minutes Ongoing = current time is between start_time and end_time Ends Soon = ends within 45 minutes Tonight = starts later today after current time Tomorrow = starts tomorrow This Weekend = starts Friday through Sunday Upcoming = future item within 14 days Open Now = buddy/place/experience available now Last Call = capacity almost full or event ends soon Action Needed = user has host/buddy/safety/request task My Plan = user already joined or saved 

Do not show ended events/trips/circles as active.

Cancelled, deleted, hidden, reported, unavailable, and completed items should not show unless the card is specifically for owner/host management and clearly labeled.

---

# 6. User relationship states

Cards must reflect the user’s relationship to the item.

Supported states:

txt joined saved hosting pending requestable invite-only full waitlist ongoing starting-soon ending-soon available unavailable cancelled completed location-off privacy-limited action-needed 

Required behavior:

txt Joined → Open / Open Crew Saved → View / Join Hosting → Manage / Message Attendees Pending request → Pending / View Full → Waitlist or View Invite-only → Request Requestable → Request Buddy available → Request Buddy / Message Buddy request received → Review / Accept / Decline Safe Return due → Check In / Open Safety Cancelled → Hidden from normal users Ended → Hidden from normal users Unavailable buddy → Hidden or View Only Location off → Show trip-city/saved-city content, not live-location content Privacy-limited → Do not show private/live-location-dependent item

# 8. Ranking priority

When many items exist, rank by urgency and relevance.

Priority order:

txt 1. Safe Return / urgent safety items 2. User’s joined events/trips starting soon 3. User’s saved events/trips starting soon 4. Host/buddy/circle/trip requests requiring action 5. Ongoing events in user’s trip city/current city 6. Active Trip Crew or Circle activity 7. Rent a Buddy availability for today 8. Events/trips/circles matching interests, language, and availability 9. Hidden Gems near user/trip city 10. Compass-backed picks 11. General upcoming items 

Do not allow random general events to outrank user-owned or urgent items.

# 9. Deduping rules

If the same object qualifies for multiple reasons, show it once.

Example:

txt Rooftop Drinks Reasons: Starts soon · Your circle is going · Matches nightlife 

Do not show duplicate cards for the same event/trip/circle/buddy/place.

Deduplicate by stable object identity:

txt item_type + item_id 

---

# 10. Context switching

Live Pulse must support context.

Possible contexts:

txt Near Me Current City Upcoming Trip City Saved City Specific Trip Specific Circle My Plans 

The app should not assume the user only cares about their physical location. A traveler in Florida may be planning Tokyo.

If location is denied/off, use:

- selected city
- upcoming trip city
- saved city
- user’s joined/saved plans
- general Discovery picks

Do not use live location if location permission or privacy settings do not allow it.

# 11. Privacy and safety filtering

Live Pulse must respect:

- blocked users
- users who blocked the viewer
- reported/hidden content
- private events
- private trips
- private circles
- invite-only rules
- age limits if implemented
- language filters if implemented
- trust thresholds if implemented
- location privacy
- Trip Crew visibility
- Find Your Circle visibility
- Rent a Buddy approval status
- capacity
- cancelled/completed/deleted status
- user availability
- city launch status if present

Live Pulse must never expose:

- exact private live location
- private trip/circle membership
- blocked users
- hidden/reported content
- unavailable buddies as bookable
- private events as public
- full events as joinable unless waitlist exists
- fake payments
- fake bookings
- fake safety escalation

- title
- date/time when time-based
- city/location or valid context
- host/owner
- visibility status
- join/request rules
- valid detail route
- valid action target

Do not show a buddy if missing:

- approved/visible status
- city/area
- service type
- availability
- request/message action
- safety boundary language

Do not show cards that cannot route correctly.

# 13. Card expiration rules

Each Live Pulse item must expire or change state correctly.

txt Starting soon event → becomes ongoing when it starts Ongoing event → removed or completed when it ends Ends soon event → removed when ended Join request → removed when accepted/declined/cancelled Buddy request → removed when accepted/declined/expired/cancelled Safe Return reminder → removed when completed/cancelled/escalated Hidden Gem → removed after session/day unless saved Compass Pick → expires after refresh window Full event → hidden as joinable unless waitlist exists Cancelled event/trip/circle → hidden from normal rail 

No stale cards should stay in the rail.

---

# 14. Refresh behavior

Live Pulse should update without spamming the backend.

Refresh rules:

txt Refresh on Pulse open Refresh on pull-to-refresh Refresh after join/save/request/accept/decline/check-in actions Refresh when context city/trip changes Refresh every few minutes while Pulse is open Do not refresh every second Do not create duplicate cards after refresh Do not lose user state after refresh 

If realtime is available, use it carefully for notifications/messages/activity, but still support manual refresh fallback.

# 17. “Do not show again” behavior

- Hidden Gems
- Compass picks
- general event suggestions
- create prompts

Store dismissals so dismissed cards do not immediately reappear.

# 23. External dependency fallback

If a dependency fails:

txt Maps API fails → hide directions/map-specific action or use list view Location denied → show selected/trip/saved city context Realtime fails → allow manual refresh Recommendation service fails → show joined/saved/upcoming items from direct data AI/Compass fails → hide Compass-backed cards, keep real event/trip cards Storage/media fails → show fallback image/avatar Database error → show retry state 

Do not allow external failures to make Pulse blank.
