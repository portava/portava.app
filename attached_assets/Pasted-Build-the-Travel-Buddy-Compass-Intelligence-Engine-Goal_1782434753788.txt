Build the Travel Buddy Compass Intelligence Engine.

Goal:
Create the core app-wide intelligence system that governs what users see, how they see it, when they see it, why they see it, and how fast it loads. Compass should make Travel Buddy smarter, safer, faster, more personalized, more adaptive, and more rewarding for active high-quality users.

Important:
Compass is not just a feed algorithm.
Compass is the operating brain of Travel Buddy.

Compass must govern:
- Discovery feed
- City Pulse
- Events
- Trips
- Rent a Buddy
- Telegraph suggestions
- Hidden Gems
- Passport Stamps
- Nearby travelers
- Group plans
- Notifications
- Safety prompts
- Delayed posting
- Search suggestions
- Active-user visibility rewards
- Content front-loading and caching

Core principle:
Safety, privacy, eligibility, and user controls must always run before ranking, boosting, front-loading, or personalization.

Hard law:
Safety Filter → Eligibility Rules → Privacy Guard → Front Load Eligibility → Scoring → Diversity → Explanation → Display

Never do:
Scoring → Safety
Front-load → Permission Check
Boost → Safety Filter

Compass system rules:
- Safety beats engagement.
- Privacy beats personalization.
- Eligibility beats ranking.
- User explicit controls beat algorithm guesses.
- Admin pause beats all recommendations.
- Fresh safety state beats cached feed.
- Active-user rewards cannot override safety.
- Sponsored/boosted content cannot override safety.
- Front-loaded content must be permission-checked before it reaches the client.
- Never trust client-side hiding as privacy.

8. Compass Diversity Engine:
Prevent repetitive feeds.

Rules:
- Do not show too many cards from one category in a row.
- Do not show too many posts from the same user.
- Do not show the same Buddy too often.
- Do not let nightlife dominate the feed.
- Do not let paid/featured content dominate the feed.
- Rotate safe new users/events/Buddies.
- Mix discovery, social, safety, trips, posts, and Passport opportunities.
- Respect user ignores and fatigue.
- Add exploration content so users discover new things.

Example feed mix:
- Tonight near you
- Compass Picks
- Travelers you may vibe with
- Rent a Buddy available now
- Events during your free time
- Hidden gems near your trip
- Passport Stamp opportunities
- Safety tip/Safe Return reminder
- Trending City Pulse posts
- Plans your Circle may like

9. Compass Fair Exposure Engine:
Give new safe contributors a chance without overriding safety.

Fair exposure rules:
- New verified users get limited exposure tests.
- New approved Buddies get limited safe exposure.
- New events get a fair test window.
- New hosts can be shown if verified and eligible.
- Exposure is capped.
- Fair exposure ends if reports, no-shows, spam, or safety flags appear.
- High performers can earn more exposure.
- Overexposed users get temporary cooldown.

10. Compass Active User Reward Engine:
Reward active, safe, helpful users by pushing their feeds, posts, events, profiles, and booking surfaces to more compatible people.

Important:
Reward contribution, not attention.
Reward quality, not spam.
Activity alone should not override safety.

Active User Score should be separate from Trust Score.

Trust Score = can this person be trusted?
Active User Score = how much are they contributing?
Compass Visibility = should we show them more, to whom, and where?

Reward high-value activity:
- completed event attendance
- successful hosted event
- completed Rent a Buddy booking
- positive review from verified/high-trust user

Before nighttime:

- transport-home options
- delayed posting defaults

During Rent a Buddy booking:
- booking detail
- Telegraph thread
- safety panel
- emergency button

- Add Time options
- delayed posting rules
- tagging consent flow

After leaving location:
- delayed post publish check
- Passport Stamp credit
- review prompt

- nearby next recommendation

Front-load security:
Never preload sensitive data unless the same user is authorized to view it right now.
Never preload private exact location, ID documents, emergency contacts, admin notes, unpublished posts, blocked content, restricted age/category content, or messages the user is no longer allowed to access.
Backend must permission-check before sending data.

Front-load scoring:
Preload Score =
Likelihood User Opens It
+ Safety/Critical Priority
+ Time Sensitivity
+ Trip Relevance
+ Active Booking Relevance
+ Message Urgency
+ Low Cost To Load
- Heavy Media Cost
- Staleness Risk
- Privacy Risk
- Low Network Penalty

Device/network awareness:
If fast Wi-Fi:
- preload images, map pins, next feed page, top profiles.

If slow connection:
- preload text, small thumbnails, safety tools, first feed.

If low battery:
- pause heavy background loads.

If cellular:
- reduce video previews and large media.

If active safety mode:
- prioritize safety, messages, route, emergency tools.

Media loading:
- thumbnails first
- lazy-load full images
- do not preload full videos unless likely
- preload first frame for video
- compress feed media
- prioritize visible cards
- cancel media loads when user scrolls away
- cache profile pictures/category icons
- use skeleton cards or blurred previews

Performance requirements:
- First feed response should use cached safe feed when available.
- Tier 0 data must load first.
- Safety-critical state must not rely on stale cache.
- Feed should support pagination.
- Media should lazy-load.
- Full videos should not preload unless likely and network allows.
- Background refresh should not blank the feed.
- Preload must be cancellable/limited.
- Cache invalidation must happen on safety/privacy/eligibility changes.

Testing:
Add tests for:
- Safety filter runs before scoring.
- Eligibility runs before front-load.
- Private data is never preloaded for unauthorized users.
- Blocked users do not appear in feed or preload.
- Delayed posts do not appear before eligible.
- Active Safe Return prioritizes safety content.
- Rent a Buddy active booking preloads safety panel and Telegraph thread.
- Slow network reduces media preload.
- Cached feed returns quickly and refreshes in background.
- Cache invalidates when user blocks/reports someone.
- Cache invalidates when admin pauses city/category.
- Cache invalidates when Buddy approval changes.
- Front-load never sends ID docs/emergency contacts/private coordinates.
- “Why am I seeing this?” returns safe explanation.
- Feedback changes future ranking.
- Hide category reduces that category.
- Active-user reward boosts safe helpful users.
- Active-user reward does not boost users with severe safety flags.
- Spam activity does not increase visibility.
- No-show reduces visibility.
- New verified users receive limited fair exposure.
- Overexposed users enter cooldown.
- User can disable active visibility boost.
- Admin can remove/restore boost eligibility.
- Abuse detection flags suspicious review rings.
- Compass fallback mode returns safe basic feed.
- Admin can preview feed in testing sandbox.
- Admin can roll back algorithm version.
- Notification engine does not push ineligible content.
- Safety alerts outrank discovery notifications.
- Public APIs do not expose private location or moderation data.
- Compass works when COMPASS_ENABLED is off by falling back safely.

Acceptance criteria:
- Compass governs the Travel Buddy experience across feed, discovery, posts, events, Rent a Buddy, Telegraph suggestions, notifications, safety prompts, delayed posting, and front-loading.
- Safety, privacy, eligibility, and user controls always run before ranking or preload.
- Feed is personalized, explainable, diverse, and fast.
- Front-load system makes likely next screens feel instant without leaking private data.
- Active, safe, high-quality users earn more visibility.
- Spammy or risky activity reduces visibility.
- Users can control preferences and visibility rewards.
- Admin can audit, tune, pause, test, and roll back Compass.
- Fallback mode keeps the app usable if Compass fails.
- Tests prove governance, security, performance, active-user rewards, cache invalidation, explainability, and privacy behavior.
