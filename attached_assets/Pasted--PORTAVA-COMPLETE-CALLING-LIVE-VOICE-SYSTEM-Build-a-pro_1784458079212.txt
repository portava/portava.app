# PORTAVA — COMPLETE CALLING & LIVE VOICE SYSTEM

Build a production-ready calling system across Portava using one shared calling architecture.

This is an extension of the existing Telegraph messaging, Rent a Buddy, Trips, Trip Crews, Circles, and Events systems.

DO NOT build isolated calling implementations for each feature.

All calling must use the same:

- Call service
- LiveKit integration
- Permission engine
- Block/safety rules
- Call session model
- Notification system
- Realtime signaling
- Call history
- User calling preferences
- UI components
- Analytics
- Abuse protections

The goal is to keep Portava users inside Portava instead of forcing them to exchange phone numbers or move conversations to WhatsApp, FaceTime, Messenger, Telegram, etc.

---

# 0. NON-NEGOTIABLE ARCHITECTURE RULE

There must be ONE canonical Portava calling system.

Telegraph, Rent a Buddy, Trips, Trip Crews, and Events are contexts that consume it.

The architecture should be:

PORTAVA CALL SERVICE

↓

Direct Calls
- Telegraph
- Rent a Buddy

Group Calls
- Trip Crew

Live Voice Rooms
- Events

↓

Shared LiveKit Infrastructure

↓

Shared Permission + Safety Layer

Never create separate conflicting systems such as:

- telegraphCallService
- rentABuddyCallService
- tripCallService
- eventCallService

Context-specific adapters are acceptable.

Separate sources of truth are not.

# 8. CANONICAL CALL PERMISSION ENGINE

Examples:

canUserJoinCall(...)

canUserModerateCall(...)

The permission layer should understand contexts such as:

- telegraph_dm
- rent_a_buddy
- trip_crew
- event_room

For 1:1 calls verify:

1. Caller is authenticated.
2. Target thread exists.
3. Caller is a participant.
4. Callee is a participant.
5. Existing messaging permissions allow communication.
6. Neither side has blocked the other.
7. Callee's calling preferences allow the call.
8. Thread/context remains valid.
9. Rent a Buddy context remains eligible when applicable.
10. User is not suspended/restricted from calling.
11. Caller is not rate-limited for call spam.

For group calls verify:

1. User is authenticated.
2. Group/event/trip exists.
3. User has required membership.
4. User has not been removed/banned.
5. Participation remains valid.
6. Trust rules are respected.
7. Age restrictions are respected.
8. Safety/block rules are applied appropriately.
9. Room is active and joinable.
10. User is not restricted from calling.

Authorization must happen server-side.

Do not rely only on hidden/disabled client buttons.

# 11. LIVEKIT ARCHITECTURE

Use LiveKit Cloud.

Secrets:

LIVEKIT_URL

LIVEKIT_API_KEY

LIVEKIT_API_SECRET

Never expose LIVEKIT_API_SECRET to the mobile client.

Backend mints short-lived LiveKit access tokens.

Every token request must pass Portava authorization first.

Use opaque secure room identifiers.

Do not use predictable room names such as:

thread_123

event_456

trip_789

A user must not be able to guess a room name and bypass Portava authorization.

LiveKit connection is NOT proof of authorization.

Portava remains the source of truth.

# 12. SERVER-SIDE ROOM LIFECYCLE

The Portava backend must control LiveKit room lifecycle.

Never rely exclusively on clients disconnecting correctly.

When a call is:

- Ended normally
- Force-ended
- Canceled
- Terminated because of blocking
- Terminated because of moderation
- Auto-ended because of duration limit

the backend must also terminate/delete the associated LiveKit room through the LiveKit server API where appropriate.

Synchronize:

- Database call session state
- Participant state
- LiveKit room state

---

# 13. LIVEKIT WEBHOOKS

Implement authenticated LiveKit webhook handling.

Verify supported event names against the installed/current LiveKit SDK before implementation.

At minimum handle relevant events such as:

- room_finished
- participant_joined
- participant_left

Use webhooks to reconcile:

- call_sessions
- call_participants
- joined_at
- left_at
- active state
- ended state

Webhook requests must be cryptographically verified using LiveKit's official verification mechanism.

Never trust unsigned webhook payloads.

Webhook processing must be idempotent.

Duplicate webhook delivery must not corrupt state.

- App is force-closed
- Network disappears

- Client fails to call /end
- Process is killed

Do not leave permanent:

records for rooms that no longer exist.

# 15. MAXIMUM CALL DURATION / COST GUARD

Set a hard maximum call duration of:

4 hours

Define this as a centralized configuration value.

Do not scatter magic numbers.

Warn connected users shortly before automatic termination when technically practical.

Example:

Your call will end in 5 minutes.

At the maximum duration:

1. Mark call as ending.
2. Terminate LiveKit room server-side.
3. Update call session state.
4. Update participant state.
5. Write contextual call-history entry.
6. Prevent stale reconnect attempts.

A forgotten room must never consume unlimited media minutes.

→ Server validates permission.

Calling is NOT complete merely because two devices can connect to LiveKit.

The system is complete only when:

- Telegraph voice calls work
- Telegraph video calls work
- Rent a Buddy voice calls work
- Rent a Buddy video calls work
- Trip Crew group voice works
- Event Voice Rooms work
- Incoming calls work
- Push notifications work
- Permissions are server-side
- Blocks are enforced
- Blocking force-ends direct calls and LiveKit rooms
- User calling settings are enforced
- Trust rules are enforced
- Age/event eligibility is enforced
- Call history appears in context
- Missed calls work
- Minimized calls work
- Reconnection works
- Ghost calls self-heal
- LiveKit webhooks are verified
- Rooms terminate server-side
- Four-hour maximum call duration is enforced
- Abuse protections exist
- Group moderation works
- Unauthorized users cannot mint/join rooms
- LiveKit secret never reaches the client
- Device-test gate passes
- Tests pass
- Typecheck passes
- Existing Telegraph has no regressions
- Existing Rent a Buddy has no regressions
- Existing Trip/Event functionality has no regressions
- Native build configuration is documented and verified

Start with the LiveKit prerequisite check.

Then perform PHASE 0.

Return the complete Phase 0 audit and proposed sequential task breakdown before proceeding into major implementation.

Do not rebuild Portava.

Do not redesign unrelated systems.

Extend the existing production architecture safely.

ONE Portava Call Service.

ONE permission and safety layer.

ONE call-session source of truth.

ONE LiveKit integration.

All Portava calling contexts consume this canonical system.
