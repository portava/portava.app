Fix the scroll architecture across all main Portava app pages.

CURRENT PROBLEM

The page headers, search bars, filter bars, location selectors, category tabs, availability controls, and other top sections remain fixed/sticky while only the content area below them scrolls.

This causes the user to see only a small fraction of the actual page content, especially on smaller phones.

Examples visible right now:

PULSE
- Main Portava top header remains fixed
- "Pulse"
- "Nothing live nearby right now"
- My City
- Availability
- Pulse filters
These consume a large portion of the screen while the feed scrolls separately underneath.

DISCOVERY
- Search bar
- Discover title
- City selector
- Filter/category controls
- Places/Food/List/Map controls
remain fixed while only the card results scroll.

This creates a cramped viewport and makes scrolling feel disconnected and unnatural.

REQUIRED BEHAVIOR

The WHOLE PAGE must scroll as one connected vertical surface.

The page header and page content must belong to the same primary scroll container.

When the user scrolls down:

1. The page-specific header should scroll upward with the content.
2. Large page titles should scroll off-screen.
3. Location selectors should scroll off-screen.
4. Availability controls should scroll off-screen.
5. Filter/category bars should scroll with the page unless there is a very intentional compact sticky state.
6. Content cards/feed should naturally continue upward into the freed screen space.

The user should eventually be able to use almost the entire screen for content.

DO NOT keep half the screen permanently occupied by fixed headers.

BOTTOM NAVIGATION

The global bottom navigation may remain fixed.

It must:
- respect safe area
- not cover the last feed/card item
- have enough bottom content padding so the final item can scroll completely above the nav

TOP APP BAR

The very small global app bar may remain persistent only if truly necessary.

However:

- It must not consume excessive vertical space.
- Page titles and page-specific controls must NOT be permanently fixed underneath it.
- Avoid stacking several fixed headers.

Preferred architecture:

GLOBAL SMALL APP BAR — optionally fixed

PAGE HEADER
PAGE TITLE
LOCATION
AVAILABILITY
FILTERS
CONTENT

All of the above page-specific elements should live inside ONE SCROLLABLE PAGE.

Example:

Discover

Only ONE compact row may optionally stay visible.

Do not keep the entire original header fixed.

Any sticky implementation must:

- collapse smoothly
- not jump
- not change content height repeatedly
- not interfere with scroll gestures
- not cause bounce
- not create nested vertical scrolling

CRITICAL SCROLL ARCHITECTURE RULE

ONE primary vertical scroll container per screen.

Avoid:

ScrollView
  fixed header
  ScrollView
    FlatList

ScrollView containing FlatList with scrolling enabled

Avoid competing nested vertical gesture handlers.

Prefer:

FlatList / FlashList
  ListHeaderComponent
  items

or:

ScrollView
  complete page content

for short static pages.

Use FlatList/FlashList for long or dynamic feeds.
