New task: Build the full Travel Buddy Passport page.

Goal:
Finish the full Passport page as a clean, polished, mobile-first travel identity page.

The Passport page should feel like a public travel profile and memory wall, not a settings dump.

Core product rules:
- Passport is the user’s travel identity page.
- Postcards are the main Passport experience.
- The Postcards tab must be the first tab.
- The Passport page must load directly into the Postcards tab by default.
- Keep the profile header clean and organized.
- Limit anything between the main profile info and the tab wall.
- Move account/profile controls into a Settings menu.
- Minimize interests on the main profile.
- Do not leak private/trip_only/live-location/exact GPS data.

SECTION 1 — Page structure

Passport page layout should be:

1. Clean profile header
2. Compact stats row
3. Owner/public action row
4. Tab wall
5. Active tab content

Tab order must be:

1. Postcards
2. Stamps
3. Trips
4. Map
5. About

Postcards must:
- be first
- be selected by default
- be the landing section when Passport opens
- show postcard cards immediately if the user has postcards
- show a clean empty state if no postcards exist

Do not make About, Stats, Interests, Map, or Settings the landing section.

Do not add large sections between profile info and the tab wall.

SECTION 2 — Clean profile header

The Passport profile header should show only the most important public-facing info.

Show:
- avatar/profile picture
- display name
- @username
- short bio
- home base/current city if set
- follow button for public viewer if follow UI exists
- owner action/settings menu for owner
- compact visibility badge if useful

Do not overload the profile header with:
- long interests lists
- account settings
- username forms
- privacy controls
- notification settings
- full travel preferences
- large onboarding checklist
- detailed edit forms
- oversized stat cards

The main profile should answer:
“Who is this traveler?”

Everything else belongs in:
- Settings
- About tab
- Postcard card actions
- owner-only menus

SECTION 3 — Minimize interests

If interests exist, minimize them on the main profile.

Rules:
- show max 3 interest chips on the profile header
- if more than 3, show “+N more”
- move full interests list to About tab and/or Settings
- move full interests editing to Settings
- do not show a large interests block before the tab wall

Example:
Beach • Nightlife • Food +4 more

If no interests:
- public viewer sees nothing
- owner sees a small prompt in Settings or profile completion, not a big empty section

SECTION 4 — Compact stats row

Show compact stats under the profile info.

Stats:
- Postcards
- Verified stamps
- Countries
- Cities
- Trips

Optional if follow backend/UI exists:
- Followers
- Following

Rules:
- stats must be compact
- no giant cards before tabs
- no NaN/null/undefined
- stats wrap cleanly on mobile
- removed/deleted/hidden content should not inflate public stats
- private content should not inflate public stats unless owner view clearly labels it

Verified stamp count:
- only GPS-verified, stamp_eligible postcards count as verified stamps

Manual tags:
- count as tagged memories only
- do not count as verified stamps

Create a clean owner-only action menu instead of scattered buttons.

Owner action menu items:

Optional if already supported:

Public viewer should never see owner actions.

SECTION 8 — Username system

Users should be able to:
- choose username on signin/onboarding if missing
- change username from Passport Settings
- change username from Settings page/profile section if that exists

Username rules:
- unique
- lowercase normalized
- 3–24 characters
- letters, numbers, underscores, periods only
- no spaces
- reserved names blocked
- displayed as @username

Reserved names:
- admin
- support
- system
- travelbuddy
- passport
- official
- root
- api
- settings
- login
- signup
- help

API:
- GET /api/users/check-username?username=
- PATCH /api/me/profile

Security:
- API uses auth token user, not client-supplied user_id
- user can only change own username
- user cannot spoof admin/support/system
- duplicate usernames blocked server-side

Optional safety:
- add username_updated_at
- optional username change cooldown if easy
- do not overbuild cooldown if it slows first pass

SECTION 9 — Avatar/profile photo upload

Users can upload/change profile picture.

Storage:
- use existing avatar/profile-media bucket if it exists
- otherwise create/use: profile-media or avatars

Path:
avatars/{userId}/{uuid}.{ext}

Allowed types:
- image/jpeg
- image/png
- image/webp

Suggested max size:
- 5MB

Rules:
- authenticated user can upload only to own folder
- public read is okay for avatar URLs if profiles are public
- validate file type
- validate file size
- keep old avatar until new upload succeeds
- if upload fails, do not save broken avatar_url
- show useful upload errors
- do not expose service-role key

Mobile:
- use existing media picker pattern if available
- if Expo image picker is already installed, use it
- do not force package install if Replit package install is blocked
- convert local URI to Blob correctly before upload
