# FORMAT, one line per constraint:
#
#   <table>|<constraint name>|<pg_get_constraintdef(oid) verbatim>
#
# The definition is recorded VERBATIM rather than parsed into a value list. That
# is deliberate and it is the property that makes this file worth having: the
# tree side of the comparison parses its CHECK vocabularies with
# scripts/lib/canonicalVocabulary.ts's vocabularyFromCheck, and this side is
# parsed by the SAME function. One parser, two inputs. A snapshot that stored a
# pre-digested value list would be asserting the result of a second parser nobody
# can re-check, and a difference between the two parsers would read as production
# drift.
#
# '|' is safe as a delimiter, checked rather than assumed: of the 366 definitions
# captured, zero contain '|', zero contain a newline, tab or carriage return, and
# zero contain a backslash.

#
#   pg_get_constraintdef(oid) ~ '= ANY \('  OR  pg_get_constraintdef(oid) ~* ' IN \(''
#

# holds 651 in total. The 93 of those that contain a quoted literal at all were
# read and classified rather than dropped on a guess: they are range bounds,
# jsonb_typeof assertions, regex formats, cross-column shape rules, and array

# scalar vocabulary). NONE of the 285 is of the `col = ANY (ARRAY[...])` form --
# measured, by asking production for the excluded set that matches '=\s*ANY',
# which returned 0 -- so the filter drops nothing vocabularyFromCheck could read.
# pg_get_constraintdef normalises a written `IN (...)` to `= ANY (ARRAY[...])`,
# so the second half of the predicate is belt-and-braces: it matched nothing.
#
# WHAT ABSENCE MEANS HERE, because the checker turns on this and a wrong reading

# over-permissive posture canonicalVocabulary.ts takes for the same reason. The
# rejection risk is only ever in a column that IS constrained here and whose list
