Native secure storage contains the payload; AsyncStorage contains only chunk identifiers. Browser storage uses nonextractable AES-GCM keys in IndexedDB. Real Chromium verification now covers reload/replay, tampering, cross-tab key creation, account clearing during encryption, and cancellation without late-write resurrection.
- Direct-to-group creation, forwarding picker, author forwarding capability control, host posting/media/link/slow-mode settings and member moderation. Uses existing authenticated server routes; DM history is not copied.
- Migration 4005: bounded stable backfill, guarded explicit cutover, join/leave bounds, durable delivered/seen membership watermarks, atomic monotonic ACK, same-timestamp ordering, and a shared lock order with unsend. Existing timestamp seen markers survive backfill.
- Canonical message pages and group older-page cursors use sequence after cutover; ciphertext/client IDs are serialized and deleted content stays redacted. Inbox exposes encryption capability.
- Client receipt transport rejects stale-account responses. Delivery ACK is capability-gated and separate from foreground/viewed SEEN.

Additional canonical-page regressions are being run as part of the next check.

## Encrypted history, account isolation, and cancellation

The receive pipeline now binds history and resume requests to the captured account/session, joins the applicable pending Welcome, decrypts before display, and fails closed when native E2EE is unavailable. Ciphertext is never rendered as a body. Deleted messages clear their cached plaintext even when a page contains only tombstones. The local cache retains sent plaintext and successfully decrypted incoming plaintext because MLS generations are one-use; it does not invent recovery for ciphertext consumed before the cache existed, a missing Welcome, or a device without the corresponding keys.

Native identities, device IDs, pending KeyPackages, group state and message caches are account-scoped. All asynchronous crypto paths check the same owner/session before and after native work. SQLCipher stores the ratchet and its decrypted body in one transaction; a runtime `cipher_version` check rejects older/plain SQLite binaries before any schema or plaintext write. The old `localMessageDb` API now uses that same gated handle, actual `executeSync` API, and transactional search updates. Legacy group state is adopted only when its own MLS credential matches the signed-in account. A durable hashed consumption receipt prevents replaying private pending packages after a cleanup interruption. Identity initialization persists a recoverable bundle before individual fields, and old private Welcome material is retained in a bounded legacy slot during replenishment.

Outbox transport carries an AbortSignal and the existing owned-request timeout/HTTPS/session policy. Cancelling marks native chunks non-replayable before deletion and prevents late acknowledgement/retry writes from recreating the record. Browser writes check an IndexedDB key-generation marker in the same transaction as the message write, so another tab cannot resurrect an account-cleared draft. Failed pending messages expose **Stop retrying** in direct and group conversations. This stops local delivery attempts; it does not recall a message the server already accepted.

Migration **4014** makes KeyPackage publication and consumption atomic. Both lock the device first and persist counts from actual inventory. A private, privilege-restricted fingerprint ledger survives consumption, preventing a response-loss retry or alternate base64 padding from republishing a consumed package. Existing valid inventory is deduplicated and recounted. The migration cannot reconstruct keys already consumed before its installation. Nothing has been applied to production.

No arbitrary ratchet advancement, dropped messages or crypto-storage rewrite was introduced.

These cover credential-derived owners, create/join, matching safety numbers, Unicode/NUL encryption, process-exit restoration, two-way messages, replay/tamper/wrong-Welcome/malformed-state refusal, and old-session forward compatibility. ## Final reconciliation: references, attachments and optional feedback

Canonical object references now use the validated `portava-object.v1` codec and versioned legacy card bodies. Malformed or mismatched references cannot be recovered from an unrelated UUID subtype. Current place-card counts use bounded batched reads: the 40-card fixture needs four queries instead of 121, with exact-count and unavailable-state checks and no cross-request authorization cache.

Migration4016 journals authorized image/video/album forwarding before copying bytes. Sources must be owned application Storage paths and pass current read access; copies strip image metadata and video location metadata, use fresh forwarder paths, and finish atomically with the message and provenance. SQL rechecks source mutation, unsend, history/membership, blocks, encryption and forwarding policy. Uncertain uploads or commits retain an inaccessible cleanup journal instead of losing track of possibly stored bytes. Cleanup is bounded and retryable. Scoped server requests have a 30-second full-response deadline and a five-minute operation budget. Voice and external GIF byte-copy formats remain explicitly unsupported; the separate GIF provider flow sends an ID, never a copied external asset.

Migration4017 implements optional **self-reported** meetup feedback, default OFF and without a default retention duration. Enabling requires an integer from 1 to 365 days. Only an eligible participant in a confirmed completed plan can deliberately submit an answer. Reads never write; retries and edits do not extend retention. Responses are private, included in owner data export, removable individually or through Message settings after membership loss/plan expiry, and removed with account deletion. The withdrawal control remains reachable if message settings reads fail. Expired rows are excluded immediately and swept hourly in bounded batches even if collection is disabled. Diagnostics use durable database aggregates, suppress populations below ten distinct users, and retain admin/purpose/audit gates. They never label a response as verified attendance.

Recap startup reads availability only. Detailed content and feedback load on opening, with account/thread/plan/focus ownership and deadlines. A Close control remains visible during loading and outside the scrolling content; Done remains an equal offered outcome. Narrow layouts and direct actions were reviewed using actual components and synthetic API boundaries. Browser checks at320×568 and440×956 report zero console errors/warnings; this is not physical-device certification.

## Optional GIPHY adapter — prepared, not activated

The picker is unavailable unless `EXPO_PUBLIC_TELEGRAPH_GIF_PROVIDER=giphy` and the platform's public `EXPO_PUBLIC_TELEGRAPH_GIPHY_IOS_KEY`, `_ANDROID_KEY` or `_WEB_KEY` is configured. The server independently requires `TELEGRAPH_GIF_PROVIDER=giphy`. No provider account was created, terms accepted or key added.

The implementation follows the official [GIPHY API requirements](https://developers.giphy.com/docs/api/) and [endpoint documentation](https://developers.giphy.com/docs/api/endpoint/): requests go directly from the client to GIPHY, no application auth/person/thread IDs accompany them, order is preserved, and GIF URLs/assets are not persisted or proxied. The official Powered by GIPHY attribution is bundled unmodified. Search and pagination have bounded requests; opening a picker performs no provider request. Users search/browse and select deliberately. Only `{provider:'giphy',providerId}` is sent using `gif.v2`; old clients receive a negotiated fallback even when the general schema flag is off. Recipients explicitly load an individual GIF, resolve the ID afresh, and see still-image controls for reduced motion/data saver. Fullscreen uses one image instance and retires on background/account changes. Provider keys, terms/approval and real-service acceptance remain owner requirements.
