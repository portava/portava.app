Discovery Engine Rulings

Eight decisions on DISCOVERY_ENGINE_MODE. Each one: the question, the options, a recommendation with its reasoning, and what a wrong ruling costs. Nothing is implemented until these are ruled.

Companion to the design packet Verified at HEAD 93523f4fb Status awaiting ruling

Read first — what the rollout can and cannot prove

Shaping fact 1

Shadow mode cannot tell you whether users like the new engine better

Users never see the PDE order in shadow mode, so no tap, save or dwell can ever be attributed to it. Shadow answers two questions honestly — would the new engine have served something different, and how different, and what does it cost in latency and CPU. It cannot answer would users have engaged more.

That question is only answerable at Stage 4, when real traffic actually receives PDE output. This is a property of shadow deployment generally, not a flaw in this design — but it means any plan promising an engagement verdict from shadow is promising something the mechanism cannot deliver.

Shaping fact 2

There is no baseline today, so instrumentation has to come before the flag

Five of the six serve points in GET /discovery write nothing at all. The only rank_events data that exists describes authenticated cold fetches that did not take the Compass branch — the narrowest and least representative slice of what users receive.

So Stage 0 is instrumentation, before the flag exists. It is also where the first genuinely new number arrives: what fraction of discovery traffic reaches a ranker at all. If that fraction is far higher than the two-hour cache TTL implies, D5 gets cheaper and this packet's central argument weakens — which is precisely why measuring comes first.

Stage 0

Proves reach — how much traffic reaches a ranker, per serve point. No flag yet.

Stage 1

Proves the flag is a genuine no-op at legacy.

Stages 2–3

Prove divergence and cost — how differently PDE would order, and what it costs.

Stage 4

Proves engagement. The first stage that can, and not before.

The eight rulings

D1

Naming and loader

Should the mode carry a COMPASS_ prefix so the existing Compass flag loader can see it, or keep the name DISCOVERY_ENGINE_MODE and be read through the general flag helper instead?

Options

  • ACOMPASS_DISCOVERY_ENGINE_MODE, read by compass/flags.ts. Inherits a 30-second cache. Boolean only.
  • BDISCOVERY_ENGINE_MODE, read by lib/featureFlags.ts. Exact-match query, no prefix constraint, and the only helper at HEAD that reads the metadata column.
RecommendB

The mode is three-valued and metadata is the only place a third value can live, which option A forecloses. Naming a discovery-wide execution switch COMPASS_ would also misdescribe it, since two of its three modes govern requests Compass never touches.

If ruled the other way

A forces D2 onto its weaker options and hands the flag to a loader that returns false for every Compass flag on any database error. The prefix trap stays one well-meant rename away from silently disabling the switch with no error and no log line.

D2

How three values ride a boolean column

Given that feature_flags.enabled is a boolean, how should a three-valued mode be represented?

Options

  • AOne row: enabled as master on/off, metadata.mode ∈ {legacy, shadow, pde}.
  • BTwo boolean rows with a precedence rule between them.
  • CA dedicated column on feature_flags.
RecommendA

It uses only what already exists in the schema and cannot express a contradictory state. The honest cost is that metadata is untyped JSON, so the parse needs a defined fallback — which is exactly what D3 settles.

If ruled the other way

B can hold "shadow and pde both on" and someone has to remember the precedence rule during an incident. C means a migration on a table shared by 168 live flags to serve one consumer.

D3

Failure polarity and the emergency stop

What should a missing row, unparseable metadata, an unknown mode string, or a database error resolve to — and should PDE get its own kill switch?

Options

  • AAll four cases resolve to legacy. One rule, no second flag read.
  • BA, plus a separate disable_discovery_pde stop read through isKillSwitchEngaged, whose polarity engages on an unreadable state.
RecommendB

A is correct for the mode itself but leaves PDE with no stop that survives the database being unhealthy. B costs one extra read on the PDE path only, and reuses a helper whose inverted polarity is already reasoned about and documented in the tree.

If ruled the other way

Under A alone, the moment you most want to halt PDE — something is wrong, the database is struggling — is the moment the flag read is least trustworthy, and the fallback quietly keeps PDE running rather than stopping it.

D4

Scope of the flag versus scope of the baseline

Should the flag govern only GET /discovery, and should the Stage 0 baseline cover more ground than the flag does?

Options

  • AFlag on GET /discovery only — the six serve points where ranking exists to be replaced.
  • BAlso /discovery/feed, which serves places with no ranking and no caching at all.
  • CAll ten serve points across all five routes.
RecommendA for the flag, C for the baseline

Search and suggest have no ranker to switch, so putting them under the flag buys nothing. But the baseline must cover everything users receive, or the comparison is once again computed on a subset.

If ruled the other way

Narrowing the baseline to match the flag reproduces the exact error the owner directive names — measuring on traffic that is not representative of what users get. Widening the flag to search and suggest takes on two routes with nothing to switch.

D5

What PDE caches — the consequential one

Should the new engine cache post-ranking per user, cache the candidate set user-independently and rank on every request, or keep today's cache structure?

Options

  • ACache post-ranking, per user. Correct personalisation; the user-independent cache disappears.
  • BCache candidates user-independently, rank every request. External call volume unchanged; ranking CPU moves to every request.
  • CKeep today's structure.
RecommendB

It separates the two things today's design conflates: candidate retrieval, which is expensive, external, rate-limited and genuinely user-independent, and ranking, which is cheap, internal and inherently per-user. Cache A currently serves both, which is the precise mechanism by which personalisation reaches one user in N.

If ruled the other way

A collapses the cache hit rate on a rate-limited external dependency and can leave discovery slower and more fragile than it is today. C reproduces the defect exactly — P1 would ship a new ranker with the same reach as the old one, and the whole exercise returns nothing.

D6

How much traffic shadow runs on

Should shadow mode run on internal accounts, on a fixed sample of real traffic, or on everything?

Options

  • AInternal accounts only.
  • BA fixed small percentage, hashed on user id so a user's experience is stable.
  • CAll traffic.
RecommendA, then B

A proves the harness end to end at essentially no risk or cost; B is what actually produces the divergence measurement across real cities and real cache states. Shadow doubles ranking work on every request it covers, so the ceiling is worth setting deliberately rather than by default.

If ruled the other way

C pays the full doubled cost before anyone has confirmed the harness works. Stopping at A leaves a sample too small to characterise divergence across cities and cache states, so Stage 4 would launch on a signal that does not generalise.

D7

Where shadow observations are written

Should shadow rows go to a new table, or into rank_events under a new surface value?

Options

  • AA new append-only table, discovery_shadow_serves, joined to outcomes offline.
  • Brank_events with a new surface value, widening a CHECK constraint.
RecommendA

rank_events is mutable state, not a log: an outcome UPDATEs the impression row in place, and the outcome route takes surface from client input. A new table is append-only by construction and lets the 90-day retention policy cover it explicitly from day one.

If ruled the other way

Under B a shadow impression can absorb a real user outcome, permanently, and afterwards there is no way to distinguish a contaminated row from a clean one. That corrupts the same funnel the comparison depends on.

D8

Whether the baseline breaks the metrics series

Should Stage 0 write real rank_events impressions for cache-served traffic, accepting that the existing admin metrics series becomes incomparable across the cutover?

Options

  • AReal impression rows on every serve point. Outcomes attach normally. Insert volume rises by roughly the cache-hit multiplier.
  • BWrite the baseline to the D7 table instead. History stays intact; outcomes do not attach.
RecommendA, with the discontinuity announced in advance

B preserves a metric series whose defining property is that it describes one unrepresentative serve point. The break is a one-time, dated cost; the blindness B preserves is permanent.

If ruled the other way

Under B, no outcome can ever attach to cache-served traffic, so the engagement question stays unanswerable for the great majority of serves — including every serve point where PDE is expected to make the most difference.

One thing that would change these recommendations

The measurement that could overturn D5

If Cache A's real hit rate is far lower than its TTL implies

Heavy invalidation, frequent restarts, or many empty-Overpass keys would all mean more traffic reaches a ranker than the analysis concludes. In that case the "one user per city per two hours" figure is too pessimistic, D5 becomes materially cheaper, and option C stops being indefensible.

Stage 0 measures this directly, which is why it is sequenced before the flag rather than after it. No ruling here is irreversible on the strength of an unmeasured assumption.
