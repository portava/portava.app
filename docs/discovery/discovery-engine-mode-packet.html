Discovery Engine Mode

A request-level switch over which discovery execution path serves a request — not a wrapper around the ranker. Eight decisions for the owner, the mechanics that follow from them, and the costs stated at full size.

Flag DISCOVERY_ENGINE_MODE Modes legacy / shadow / pde Verified at HEAD 93523f4fb Status design only — no implementation until ruled

The directiveWhat the flag has to be

The flag must control which overall discovery execution path handles the request, not merely wrap the ranker, because the production cache path can bypass ranking entirely, and the old-vs-new comparison must measure actual behaviour users receive rather than new-ranker-vs-old-ranker on traffic that never reaches either ranker.

Owner directive, verbatim

Phase −1 verified this directive against the tree rather than assuming it. It holds, and the mechanism behind it is sharper than the wording suggests. The rest of this packet is built on the verified topology, recorded in full at docs/discovery/phase-minus-1-repository-proof.md.

01 — EstablishedWhy wrapping the ranker cannot work

Three verified facts, in the order that makes the conclusion unavoidable.

The two caches are in series, not in parallel

The Cache A check at routes/discovery.ts:1113 returns before the Compass block at :1211 is reached. There is no fork. Cache A gates everything downstream of it, including both rankers.

Cache A is shared between users; the ranked output is not

Cache A's key is cacheKey(destination, category, radiusKm) (:159‑161, used at :1025) — no user term. On a cold fetch the raw, pre-ranking Overpass list is written to that shared key at :1204. The personalised ranking that happens afterwards at :1242 is stored only under the requesting user's own Cache B key at :1263.

The consequence

For a given city, category and radius, the Compass ranker runs at most once every two hours, its output is served to exactly one user — the one who happened to trigger the cold fetch — and every other user for the next two hours receives the unranked Overpass order.

A flag that wraps the ranker therefore switches an engine that almost no request reaches. It would report a clean A/B result computed over roughly one request per city per two hours.

Cache B is close to vestigial

Cache B's TTL is 10 minutes (:152); Cache A's is 2 hours. Cache B is only consulted after Cache A misses, so in steady state its entry is dead 1h50m before the next miss can occur. It is reachable only when Cache A is not written — both writes sit inside one if (enrichedOsm.length > 0) guard at :1203 — or on concurrency, invalidation, or process restart. Instrumenting Cache B to measure the ranker would measure almost nothing.

And a related trap: only one serve point logs

GET /discovery has six serve points. Exactly one of them writes a rank_events row (:1433). Both Compass branches respond and return before it. So today's surface='discovery' data describes only authenticated cold fetches that did not take the Compass branch — the narrowest and least representative slice of served traffic.

03 — PlacementAbove the cache fork

The dispatch belongs immediately after request parameters resolve and before the Cache A check — between :1026 (where key and cached are computed) and :1113. That is the only position from which a mode can claim a request that would otherwise be answered from cache without ranking.

Placing it anywhere below :1113 reproduces exactly the defect the directive names. Placing it above :1025 means the mode cannot see the cache key, which shadow mode needs for attribution.

The three modes

ModeWho serves the userWhat else runsWhat is written
legacyToday's path, unchanged — all six serve points intactNothingWhatever today writes, plus a serve-point observation (Stage 0)
shadowLegacy, always. The user's response is byte-identical to legacyPDE computes a result after the response is flushedBoth orders, the legacy serve-point id, and both timings — to a separate table
pdeThe new engine, including its own caching policyLegacy is not runReal impressions on the PDE path

shadow is the mode that makes the directive's second half achievable: it observes what users actually received on every serve point — including the four that run no ranker — instead of comparing two rankers on traffic that reaches neither.

04 — For the ownerDecision points

Eight rulings. Each carries a recommendation; none is implemented until ruled.

D1 · Naming and loader

Which flag system reads the mode

Phase −1 confirmed the trap: compass/flags.ts:29 loads flags with .like("flag", "COMPASS_%"), and isEnabled returns flags[flag] ?? false at :53. A DISCOVERY_-named flag read through it returns false with no error, no warning and no log line, and the 30-second cache keeps it false. This is a genuinely binary choice.

  • ARename to COMPASS_DISCOVERY_ENGINE_MODE and use the existing isEnabled. Inherits the 30 s cache. But the name misdescribes a switch that governs paths where Compass never runs, and enabled is boolean-only.
  • BKeep DISCOVERY_ENGINE_MODE and read it through lib/featureFlags.ts, which queries .eq("flag", flag) with no prefix constraint and whose getFlagRow (:73‑91) is the only helper at HEAD that reads the metadata column. No caching of its own.

Recommendation — BThe mode is three-valued and metadata is the only place a third value can live. Naming a discovery-wide execution switch COMPASS_ would be actively misleading, since two of its three modes govern requests Compass never touches. The missing cache is a mechanic, not an obstacle (M5).

D2 · Representation

How three values are carried on a boolean column

feature_flags.enabled is boolean (lib/database.types.ts:5745). The table also has metadata Json | null (:5747).

  • AOne row. enabled is the master on/off; metadata.mode ∈ {legacy, shadow, pde} selects the path. Unreadable or unknown values fall back per D3.
  • BTwo boolean rows with a precedence rule. No schema surface needed, but two rows can express a contradictory state and someone must define which wins.
  • CA dedicated column. Cleanest to read, but a migration on the flags table for one consumer.

Recommendation — AUses only what exists and cannot express a contradictory state. Cost stated plainly: metadata is untyped JSON, so the parse needs a defined fallback and that fallback is D3.

D3 · Failure polarity

What an unreadable or unknown mode means

Phase −1 confirmed the two existing polarities: isFlagEnabled returns false on any error, while isKillSwitchEngaged (lib/featureFlags.ts:55‑67) returns true on a genuine error and false on a missing row — deliberately, so an unreadable stop engages.

  • AMissing row, unparseable metadata, unknown mode string, or DB error all resolve to legacy. One rule, no second read.
  • BA, plus a separate disable_discovery_pde stop read through isKillSwitchEngaged, so an unreadable stop halts PDE rather than leaving it running.

Recommendation — BA alone is sound for the mode but gives PDE no emergency stop with the correct polarity. B costs one extra flag read on the PDE path only, and reuses a helper whose polarity is already reasoned about in the tree.

D4 · Scope

Which serve points the flag governs

  • AGET /discovery only — the six serve points where ranking exists to be replaced.
  • BAdd /discovery/feed, which serves places today with no ranking and no caching at all.
  • CAll ten serve points across all five routes.

Recommendation — A for the flag, C for Stage 0 instrumentation.Search and suggest have no ranker to switch; making them PDE-aware is a different project. But the baseline must cover everything users receive, or "actual behaviour users receive" is measured on a subset again — the exact error the directive warns against.

D5 · Architecture

What PDE caches — the consequential one

This decision determines whether PDE fixes the defect or reproduces it. Everything else in the packet is plumbing by comparison.

  • ACache post-ranking, per user. Correct personalisation. The user-independent cache disappears, so the Overpass hit rate collapses and external call volume rises steeply against a rate-limited dependency.
  • BCache the candidate set user-independently; rank on every request. Keeps the expensive external call cached exactly as today. Moves ranking CPU from once-per-city-per-2h to every request.
  • CKeep today's structure. Cheapest, and reproduces the defect verbatim.

Recommendation — BIt separates the two things today's design conflates: candidate retrieval, which is expensive, external, rate-limited and genuinely user-independent, and ranking, which is cheap, internal and inherently per-user. Cache A is currently used for both, which is why personalisation reaches one user in N. B keeps the cache where it earns its keep and removes it from where it does harm.

D6 · Cost ceiling

How much traffic shadow mode runs on

Shadow doubles ranking work on every request it covers. If PDE also fetches its own candidates it doubles Overpass load, which is both the dominant latency and a rate-limited external dependency (M3 avoids this, but the ceiling is still the owner's call).

  • AInternal accounts only. Near-zero risk, and a sample too small to characterise divergence across cities.
  • BA fixed small percentage of authenticated traffic, hashed on user id so a user's experience is stable.
  • CAll traffic. Fastest signal, full cost.

Recommendation — A then BA proves the harness end to end at no risk; B produces the actual comparison. C buys speed the rollout does not need.

D7 · Where observations go

Shadow rows must not enter the impression funnel

Phase −1 confirmed rank_events is mutable state: an outcome UPDATEs the impression row in place (routes/rankEvents.ts:158‑161), the finder filters .eq("outcome","impression") at :137, and a second outcome for the same item 404s at :153 — returning before the analytics insert, so the second event produces no row at all.

  • AA new table, discovery_shadow_serves. Append-only by construction, joined to outcomes offline.
  • Brank_events with a new surface value. Requires widening a CHECK constraint (precedent: 0199_rank_events_live_pulse_surface.sql) — and because POST /rank-events/outcome validates surface from client input (:99, :107), shadow rows would become client-updatable.

Recommendation — AB lets a shadow impression absorb a real outcome, permanently, with no way to tell afterwards. A also lets the 90-day retention policy cover the new table explicitly from the start.

D8 · Baseline

Whether Stage 0 writes real impressions for cache-served traffic

Five of six serve points write nothing today. Without a baseline there is nothing to compare PDE against — but creating one is not free.

  • AReal rank_events impression rows on every serve point. Outcomes attach normally and the funnel becomes meaningful for the first time. Insert volume rises by roughly the cache-hit multiplier, and adminRankingMetrics' historical series becomes incomparable across the cutover date.
  • BWrite the baseline to the D7 table instead. Historical metrics stay intact; outcomes do not attach, so engagement stays unmeasurable on cache-served traffic.

Recommendation — A, with the discontinuity announced in advance.B preserves a metric series whose value is precisely that it describes one unrepresentative serve point. The break is a one-time cost; the blindness is permanent.

05 — MechanicsNot decisions

These follow from the rulings above. Recorded so the packet is complete, not to be ruled on.

M1

The dispatch is a single resolution point between :1026 and :1113, returning one of three values. Nothing below it changes shape in legacy.

M2

legacy is the existing code reached by falling through — not a copy of it.

A duplicated legacy path would drift from the original and quietly invalidate every comparison the flag exists to produce.

M3

Shadow computes after the response is flushed and reuses the candidate set the legacy path already assembled.

This keeps shadow off the response path entirely and holds Overpass volume flat, which is what makes D6 a question about CPU rather than about an external rate limit.

M4

A PDE error inside pde mode falls back to the legacy path within the same request and increments a counter. Users never see a mode failure.

M5

The flag read is wrapped in a 30-second TTL cache with an explicit invalidator, mirroring compass/flags.ts:9,42‑47, so D1=B costs no per-request round trip.

M6

Every observation row records the resolved mode and the serve-point id (1–6) that answered.

Without the serve-point id the data reproduces today's blindness: a row saying only "legacy served this" cannot distinguish a ranked cold fetch from an unranked cache hit, which is the entire distinction under study.

M7

The unreachable scoreWithContext else-branch at routes/discovery.ts:1423 stays in the code, untouched, and is recorded here instead.

It is a pure dead branch: discoveryCtx is assigned only at :942, inside the same if (authData?.user) block that assigns callerUserId at :925. So discoveryCtx non-null implies callerUserId non-null, and inside the else of if (callerUserId) the ternary can only ever take : places. Removing it would nonetheless orphan the whole scoreWithContext function — :1423 is its only call site — and the resulting diff would read as "removed context scoring from discovery", which is exactly the ranking change it is not. It is left alone on that ground alone, not because the analysis is uncertain.

Consequence to carry into the rollout: the unauthenticated cold-fetch serve is entirely unranked, so the legacy path has no anonymous ranking behaviour for PDE to preserve or be compared against. Whoever implements PDE should decide deliberately whether anonymous traffic is in scope rather than inheriting this by accident.

06 — CostsStated at full size

What shadow mode cannot do

Shadow mode cannot measure engagement. Users never see the PDE order, so no click, save or dwell can ever be attributed to it. Shadow answers two questions honestly — would PDE have served something different, and how different, and what does PDE cost in latency and CPU — and it cannot answer would users have engaged more. Only pde mode on real traffic answers that.

This is a property of shadow deployment in general, not of this design. It is stated here because a rollout plan that promises an engagement verdict from shadow mode is promising something the mechanism cannot deliver.

The engagement signal is lossy before anyone touches it

Because a second outcome for the same impression 404s before writing anything (routes/rankEvents.ts:153), each impression yields at most one outcome — whichever the client reports first. A user who taps and then saves produces a tap; the save is discarded entirely. Any engagement comparison inherits this, and it biases toward whichever outcome the client happens to emit earliest rather than the most valuable one. Fixing it is out of P1 scope, but no measurement built on this table should be read as if it were complete.

The rest

  • Insert volume. D8=A multiplies rank_events writes by roughly the cache-hit ratio. At 90-day retention this is a standing storage cost, not a spike.
  • Metric discontinuity. adminRankingMetrics reads rank_events. Its series breaks at the Stage 0 cutover and cannot be back-filled.
  • Ranking CPU. D5=B moves ranking from once per city per two hours to every request — the single largest recurring cost in the proposal, and the one being knowingly bought.
  • Latency. Cache A hits are currently the fastest path in discovery precisely because they skip everything. Under D5=B they gain a ranking pass.
  • Blast radius. The dispatch sits in the hottest handler in discovery. M2 keeps legacy byte-identical, which is what makes Stage 1 provable rather than merely tested.

07 — RolloutSequence and exit criteria

0

Instrument every serve point

Per D4=C and D8. No behaviour change, no flag yet — every serve point across all five routes records what it served and which point served it. This is the prerequisite for everything: today there is no baseline to compare against on five of six serve points.

Exit Every serve point emits an observation; the serve-point distribution is published. That distribution is itself the first real answer to how much traffic reaches a ranker.

1

Add the flag, default legacy

Dispatch in place per M1, resolving to legacy for every request. PDE is not written yet.

Exit Serve-point distribution is unchanged from Stage 0 within noise, and response bodies are byte-identical. A no-op that cannot be shown to be a no-op has not passed this stage.

2

Shadow on internal accounts

D6=A. Proves the harness end to end — that PDE runs, that observations land in the D7 table, that M3 keeps it off the response path.

Exit Shadow rows appear with both orders and both timings; p99 on the response path is unmoved.

3

Shadow at sample scale

D6=B. Produces the divergence measurement across real cities and real cache states.

Exit Divergence characterised per serve point — and specifically on serve points 1–4, where no ranker runs today and where the difference will be largest.

4

PDE on a small share, stop armed

First traffic where users actually receive PDE output, with the D3=B kill switch live. This is the first stage that can measure engagement at all.

Exit Engagement compared against the Stage-0 baseline on matched serve points, with the stop demonstrated to work before the share is raised.

5

Ramp

Staged increase, each step held long enough for the two-hour Cache A cycle to turn over several times.

Exit Owner ruling on full cutover, and a decision on whether legacy is retired or kept as the fallback M4 falls back to.

08 — NotesCarried forward

The post-media hold is gone, and it touched one earlier ruling

Anonymous read on post-media is revoked (src/migrations/2089_revoke_post_media_public_read.sql:101). This has no load-bearing effect on discovery: neither cache stores media bytes or signed URLs, and the ranking path reads headerImageUrl only as a boolean (routes/discovery.ts:1360) plus a completeness weight (:1361). Revocation cannot change discovery ordering, cache contents, or cache keys.

It does bear elsewhere. The staging boundary's D1 was recorded as "Forced by the post_media read-policy hold. B requires editing the held policy, so it is not available." That forcing constraint no longer exists, so D1=A is no longer forced — it may still be the right answer, but it is now a choice rather than a consequence. Two documents also still describe the policy as held and are stale prose: docs/media/staging-boundary-decisions.md:55‑57 and docs/ops/unseeded-flag-inventory.md:168. Flagged, not fixed here.

Found in passing, not P1 work

  • scoreWithContext (routes/discovery.ts:817) is unreachable. Its call site at :1423 requires discoveryCtx to be non-null inside the else branch of if (callerUserId), but discoveryCtx is only assigned where callerUserId is also assigned (:925, :942). The unauthenticated cold-fetch serve is entirely unranked.
  • A third cache exists — compass_feed_cache, per-user, via compass/CompassCacheEngine.ts. It backs Compass feed surfaces and is not imported by GET /discovery. Named here only so its "L1 Map + L2 table" shape is not mistaken for Cache A.

What would make this packet wrong

  • If Cache A's hit rate in production is far lower than its 2-hour TTL implies — heavy invalidation, frequent restarts, or many empty-Overpass keys — then more traffic reaches a ranker than section 01 concludes, and D5 gets cheaper. Stage 0 measures this directly, which is why it comes before the flag rather than after it.
  • If the owner's intended comparison is narrower than "behaviour users receive" — a ranker-quality question rather than a delivered-experience question — then D4 and D8 are over-scoped and the packet should shrink accordingly.
