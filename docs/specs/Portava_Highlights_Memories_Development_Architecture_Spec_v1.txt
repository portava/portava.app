
PORTAVA
Highlights / MemoriesDevelopment Architecture Specification
v1 • September 2026
Engineering design for the Memory Kernel, episode detection, Highlights, provenance, privacy, retrieval, projections, offline sync, lifecycle, and action loops.
Architectural thesis
Highlights are Portava’s curated window into a person’s real-world life. Memories are the private, provenance-backed graph of what actually happened. The system must remember truthfully, keep context private correctly, resurface intelligently, share without leaking private state, and turn past experience into new real-world action.

1. Architectural Mandate
The Memory domain is not a media gallery. It is Portava’s historical truth layer for user-controlled real-world experiences. Media, Trips, Events, Places, Crews, Posts, Stamps, Buddy interactions, and user-authored notes may provide evidence, but none of those objects should be silently promoted into durable history without eligibility, provenance, and privacy checks.
Hard architectural boundary
REAL WORLD
  -> signals / media / trip outcomes / user assertions
  -> evidence normalization
  -> eligibility + episode detection
  -> Memory Kernel
  -> privacy-filtered projections
  -> Highlights / Passport / Profile / Compass / Discovery
  -> real-world action
  -> new outcomes and evidence
Canonical Memory facts must remain independent from any specific viewer layout or AI-generated narrative.
Automatic Memories are private-first. Publishing is always a separate projection decision.
AI may summarize supported evidence, but may not manufacture historical facts, emotional states, participants, places, or outcomes.
Planned, saved, or nearby activity must never be represented as “experienced” without occurrence evidence or user confirmation.
Historical truth and current-world truth are separate. A place remembered as visited in 2026 does not establish that it is open now.
Non-goals
Building an Instagram Stories clone or a generic photo backup product.
Using memory capture to maximize watch time, streaks, or endless-feed consumption.
Publicly scoring users by travel volume, social value, or memory importance.
Allowing commercial ranking or sponsorship to influence whether a personal Memory is significant.
Using private Memories directly as public world-intelligence observations without a separate consent and evidence pipeline.

Truth precedence
Explicit user correction
  > explicit user assertion
  > mutually confirmed evidence
  > strong system observation
  > inference
  > unknown
A lower-confidence inference may never overwrite a higher-precedence user correction. Negative constraints from corrections must be durable so the system does not repeatedly “correct” the user back to a prior inference.

6. Evidence Normalization and Eligibility
Candidate generation begins only after evidence is normalized and passes eligibility. The eligibility gate should prevent trivial, duplicated, privacy-sensitive, or unsupported candidates from entering the user-facing pipeline.
RAW SIGNAL
 -> normalize source and time
 -> resolve entity candidates
 -> privacy/sensitivity pre-check
 -> deduplicate evidence
 -> eligibility gate
 -> episode candidate
 -> significance scoring
 -> candidate Memory
Eligibility rejection reasons
Insufficient evidence for occurrence.
Only a planned/saved activity exists.
Signal represents a pass-by rather than a visit.
Duplicate of an existing Memory/Episode.
Sensitive context is not eligible for automatic resurfacing or sharing.
Media appears downloaded/screenshot rather than captured experience.
Candidate is below triviality/significance threshold.
User or policy has suppressed inference for this class.
Evidence-source examples
Source
Strength / caveat
Explicit “Remember this”
Strong user intent; still validate entity links independently.
Trip outcome / completed plan
Strong occurrence evidence if completion itself is reliable.
GPS proximity
Weak alone; typically candidate-level only.
Camera capture timestamp/location
Useful but metadata may be wrong, edited, or imported.
Crew overlap
Supports social context but does not prove co-attendance at every episode.
Event ticket + check-in
Strong event attendance evidence.
Telegraph message
Context evidence; should not automatically become historical fact without corroboration.
Stamp issuance
Strong if stamp rules are deterministic and certified.

8. Significance and Candidate Ranking
Significance is internal orchestration, not a public social score. It controls which candidate Memories are suggested, which private Memories are more likely to resurface, and how automatic Highlights are diversified.
Inputs may include explicit remember intent, first-time or rare experiences, trip goals, meaningful social context, repeat visits, user-created captions, user favorites, unique destinations, and later user promotion. Media quality may influence presentation but must not dominate significance.
Hard rule
Explicit user intent outranks inferred significance. The system may never demote, hide, or discard a user-created Memory simply because an automated score is low.
Auto-creation vs suggestion thresholds
AUTO_PRIVATE: very high confidence + policy eligible
SUGGESTED: lower threshold; requires confirmation
NO_CANDIDATE: insufficient truth, privacy, or significance
9. Entity Resolution and Historical Identity
Memory entity resolution must preserve both canonical identity and occurrence-time display context. Historical records cannot silently rewrite themselves when places rename, merge, close, or move.
MemoryPlaceRef {
  canonical_place_id: uuid?
  unresolved_place_ref: jsonb?
  display_name_at_occurrence: text?
  location_at_occurrence: geometry?
  resolution_confidence: numeric
}
Rules
Unknown is valid; do not fabricate a place ID.
Place closure does not invalidate a historical visit.
Entity merges may repoint canonical identity while preserving occurrence-time display text.
Entity splits trigger re-resolution from retained evidence.
User correction beats automatic entity resolution.
Do not infer two unrelated IDs represent the same place merely because names are similar.
10. Privacy, Consent, and Projection Policy
Canonical Memory storage and public/social projections are intentionally separate. The private record may retain richer context than any audience is allowed to see.
Memory consent dimensions
STORE
RESURFACE
PERSONALIZE
SHARE
CONTRIBUTE_TO_AGGREGATE_INTEL
Location precision ladder
EXACT -> VENUE -> NEIGHBORHOOD -> CITY -> COUNTRY -> HIDDEN
Person visibility ladder
NAMED -> PROFILE_LINKED -> CREW_ONLY -> ANONYMOUS_COUNT -> HIDDEN
Policy invariants
Automatic Memories default PRIVATE.
Public search only queries public derivatives, never private canonical storage followed by post-query filtering.
Media visibility is independent from Memory visibility.
Publishing location must never exceed the owner’s selected precision.
Temporary operational location must not leak into durable public Highlights by default.
Being tagged or referenced does not make another user a co-owner.
Blocking and account deletion must suppress future social resurfacing and unlink profile identity as policy requires.
Public sharing must assume content can be copied outside Portava; screenshot prevention is not a privacy boundary.

14. Executable Memories
Portava’s differentiator is that the past can become a current real-world action. Memory retrieval must never simply replay old operational assumptions; the Memory provides historical context, while current engines re-evaluate feasibility.
Historical Memory
  + current world intelligence
  + current user context
  + Temporal Freedom Engine
  -> executable current plan
Actions
Do this again
Take me back
Add to Trip
Save experience
Book again if provider is currently eligible
Create a new Trip with this prior crew
Bring forward saved experiences from a previous destination
Use as inspiration while preserving novelty preferences
Historical/current fusion invariant
“You visited X in 2026” is a historical claim. “X is open tonight” requires fresh world data. Never derive the latter from the former.

Ranking dimensions

Examples

Authorized namespaces
Private personal, shared-crew, and public retrieval must have hard isolation boundaries. Public search should query only a public index or equivalent prefiltered derivative. Privacy changes must revoke searchable derivatives and embeddings.
16. Compass Contract
Compass is a consumer of Memory facts, not the owner of historical truth. It may explain and compare Memories, suggest drafts, and turn them into current actions, but it must not mutate canonical facts through prose generation.
getMemory(memoryId)

getSharedMemories(personId)
getPlaceHistory(placeId)
getTripMemories(tripId)
getMemoryEvidence(memoryId)

LLM boundary
May summarize supported evidence.
May write optional narrative style.
May propose a merge/split/correction.
May ask the minimum clarifying question when a material fact is uncertain.
May not invent emotional states, participants, place identity, attendance, preference, or historical outcomes.
May not bypass privacy/visibility policy.
May not use stale historical facts as current operational truth.

19. Offline and Multi-Device Architecture
Memory capture must work without connectivity. Use client-generated operation IDs and server-side idempotency rather than blocking on media upload or network availability.
local CREATE_MEMORY_DRAFT
 -> temp client id
 -> enqueue media uploads independently
 -> sync command with idempotency key
 -> server creates canonical Memory
 -> reconcile temp id -> canonical id
 -> late context/evidence may enrich later
Memory can exist before all media uploads complete.
A failed video upload does not invalidate already-saved Memory facts.
Concurrent edits should resolve at command/field level, not blind row last-write-wins.
Late evidence may increase confidence but must not overwrite explicit edits.
Cross-device uploads and notes should converge on one Memory/Episode where evidence supports it.
20. Media Pipeline
Media processing should be staged to control privacy, latency, and cost.
ingest metadata
 -> fingerprint / duplicate detection
 -> cheap context association
 -> thumbnail generation
 -> expensive media analysis only if necessary
 -> episode candidate enrichment
Original, viewer, card, and tiny renditions should be distinct signed derivatives.
Perceptual fingerprints may detect duplicate imports without filename dependence.
Video scenes can be logical segments without duplicating original files.
Media quality may choose representative assets for Highlights but cannot determine Memory significance by itself.
Do not make face recognition a dependency for People Memories; explicit social graph and participant evidence are safer primitives.
21. Deletion, Forgetting, and Revocation
Delete, archive, do-not-resurface, and “keep but do not personalize” are different operations and must remain separate in both data model and UX.
Action
Effect
Archive
Retain canonical Memory; remove from normal browsing unless explicitly requested.
Do not resurface
Retain and search privately; suppress proactive resurfacing.
Do not personalize
Retain Memory but exclude from preference/recommendation inference.
Make private
Revoke public derivatives and public indexing while retaining private Memory.
Delete Memory
Revoke derivatives, remove indexes/embeddings, then purge canonical/eligible evidence per policy.
Delete media asset
Remove asset and derivatives; Memory may survive if other evidence remains.
Revocation propagation must cover public projection, search index, semantic embedding, profile Highlight, Trip story derivative, Passport reference, cached narrative, and any share link. Deletion should be observable, retryable, and dead-lettered if a downstream cleanup repeatedly fails.
22. Migration from Existing Highlights / Memories
Avoid a big-bang migration. Existing IDs and URLs should remain stable where practical. Legacy media-centric records should be imported as lower-provenance Memories rather than upgraded into invented rich context.
Recommended rollout
1. Inventory current Highlights, Memories, media, Passport, profile, Trip recap, and search usage.
2. Create new canonical schema and command/event infrastructure behind existing UI.
3. Backfill legacy rows with source_mode=LEGACY_IMPORTED and conservative confidence.
4. Dual-read old and new projections in shadow mode; compare visible behavior.
5. Migrate writes to the Memory Command Bus.
6. Enable new private Memory timeline and correction tools.
7. Enable Highlight projection from new Memory Kernel.
8. Rebuild search and Passport projections.
9. Decommission legacy write paths only after parity and cleanup certification.
Never fabricate trip IDs, place IDs, participant links, or “visited” outcomes during backfill. Unknowns remain null/unresolved until evidence supports reconciliation.
23. Authorization and RLS
The Memory domain contains high-sensitivity personal history. Client roles should receive the minimum projection needed for each surface, not broad table access.
Owner-only access to canonical private Memory facts by default.
Participant membership alone does not grant full Memory access.
Public derivatives live behind explicit publication policy.
Exact location and private notes require tighter policies than public-safe summary data.
Service roles performing projections must be scoped and audited.
Search/index workers consume privacy-filtered event payloads where possible rather than raw entire rows.
Writes to evidence truth levels and inference provenance are server-controlled; clients may submit assertions/corrections but not forge “verified” truth state.
Policy functions
canReadMemory(userId, memoryId, surface)
canEditMemory(userId, memoryId)

28. Developer Rules and Non-Negotiable Invariants
1. Never treat a media asset as the Memory itself.
2. Never infer “visited” from saved/planned/nearby alone.
3. Never query a semantic substitute for an unknown canonical place/person and pretend it is the requested entity.
4. Never let AI prose write canonical historical facts directly.
5. Never let weaker inference overwrite explicit user correction.
6. Never expose private canonical Memory records to public search and rely on post-filtering.
7. Never allow public location precision above the owner’s publication policy.
8. Never keep deleted Memories in embeddings, public caches, Highlights, Passport, or Compass projections.
9. Never treat historical operational state as current intelligence.
10. Never route public-world intelligence directly from private Memory without consent/eligibility/anonymization.
11. Never swallow projection/schema failures into plausible-looking empty history without structured error state.
12. Always make derived projections rebuildable.
13. Always store provenance and engine/reason-code versions for inferred facts.
14. Always support unknown/unresolved entities truthfully.
15. Always make merge/split and publication changes auditable and idempotent.
16. Always preserve original user voice and original-language text when generating summaries/translations.
17. Always provide a deterministic fallback renderer if AI presentation fails.
18. Always measure false-memory quality before increasing automation.
29. Definition of Done
The upgraded Highlights/Memories architecture is not complete merely when the UI renders new cards. A production-ready implementation should satisfy all of the following:
Canonical Memory, Episode, Evidence, Highlight, visibility, and derivative schemas exist with migrations and live-DB checks.
RLS/policy prevents unauthorized private history access.
Create, confirm, correct, merge, split, archive, visibility-change, and delete commands are idempotent and audited.
Projection outbox and consumers survive retry/duplicate events.
Candidate detector has adversarial false-positive and false-negative fixtures.
User correction is authoritative over inference.
Public Highlight projection contains only audience-allowed fields and precision.
Public-to-private and delete revocation remove search/embedding/profile derivatives.
Compass retrieves only minimal authorized Memory context and cannot invent canonical facts.
Do Again compiles through current-world/Temporal Freedom logic instead of replaying stale plans.
Offline capture works before media sync completes.
Legacy data migration does not fabricate rich provenance.
Observability reports false-memory rate, projection lag, and revocation latency.
Private-first automatic Memory behavior is enabled only after shadow precision is acceptable.
