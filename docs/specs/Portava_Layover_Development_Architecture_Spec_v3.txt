
PORTAVA LAYOVER
Development Architecture Specification
Temporal Freedom Engine · Airport Intelligence · Real-World Orchestration

PurposeThis document is the build contract for turning Layover into a first-class Portava subsystem. It defines domain boundaries, canonical data, state machines, deterministic safety rules, event contracts, APIs, Compass integration, Map behavior, social controls, offline behavior, observability, certification, and rollout sequencing. It is intentionally implementation-oriented: developers should be able to create epics, migrations, services, tests, and release gates directly from it.

Core product thesisLayover is not “things near the airport.” It is a temporary Portava operating mode that understands what a traveler must do next, how much real-world freedom remains, what is possible under current conditions, who can participate, and how to convert that opportunity into a safe real-world action.

1. Architectural mandate
Layover must be implemented as a dedicated domain with one canonical operational truth. Trips may detect the connection, Compass may converse about it, Map may visualize it, and Safe Return may escalate it, but none of those surfaces owns feasibility. The Layover domain owns the active session and publishes certified outputs.
2. Scope and non-goals
The first production scope covers connection detection/manual creation, time budget calculation, entry/baggage/terminal constraints, airport-side vs landside eligibility, reachable experiences, dynamic return deadline, replanning, airport intelligence provenance, social presence/crew boundaries, offline fallback, and post-session outcomes. It does not require global airline booking, fully autonomous purchases, guaranteed immigration advice, or exact live airport coverage everywhere.
2.1 Non-negotiable architecture rules
Hard safety constraints are deterministic and cannot be overridden by Compass/LLM output.
Unknown critical facts reduce confidence and may fail closed for landside recommendations.
Every consequential recommendation is versioned, explainable, and replayable.
All surfaces consume the same certified LayoverSnapshot / RecommendationContract; no duplicate time-budget logic.
Commercial ranking happens only after eligibility, safety and time feasibility.
Precise social location is opt-in, temporary and automatically expires.
Missing live intelligence must degrade visibly to historical/conservative fallback; never fabricate freshness.
The system optimizes successful real-world action and safe completion, not screen time.

This service is the safety authority. It receives normalized constraints and estimates and returns a certified time/risk envelope. No LLM call is part of this calculation.

8. Reachability, routing and safe-envelope geometry
Compute bidirectional reachability: airport → candidate and candidate → airport under future return-time conditions.
Use time-based isochrone/envelope geometry, not a fixed radius.
Incorporate transport reliability, route alternatives, queue friction, weather and airport re-entry cost.
Envelope edges must contract as confidence drops or return risk rises.
Every recommendation stores the envelope/snapshot version under which it was certified.
candidate_feasible iff:
  outbound_arrival
  + minimum_experience_duration
  + conservative_return_duration
  <= hard_return_by

SafeEnvelope = union(points satisfying feasibility constraint)

Map bands:
  SAFE          = LOW risk
  TIGHT         = MODERATE/HIGH but within configured policy
  BLOCKED       = outside certified envelope

10.1 Source hierarchy and contradiction handling
Never silently merge contradictory gate/terminal/queue facts.
Preserve source provenance and conflict flag.
For safety calculations, prefer conservative values when credible sources disagree.
Community observations require plausibility checks, corroboration and decay.
Official data is not automatically “truth” when fresh contradictory evidence exists; contradiction increases uncertainty.

11.1 Replanner pipeline
1.  Normalize and deduplicate the external/internal event.
2.  Identify impacted active sessions.
3.  Recompute only the affected constraint nodes.
4.  Create a new immutable snapshot.
5.  Diff previous vs new action universe.
6.  Invalidate recommendations whose snapshot is stale or no longer feasible.
7.  Emit an OpportunityEvent only if the user’s actionable options materially changed.
8.  Notify only when user action should change.

12.1 Value-of-information rule
Before asking the user a question, determine whether the answer could materially change eligibility, safety, risk band, or the top plan. Ask the smallest number of questions required to cross the confidence threshold. Example: baggage-through status may be decisive; favorite cuisine may not be.
13. Map architecture and UI semantics
Map consumes the active snapshot and safe-envelope geometry; it does not recalculate feasibility.
Show safe/tight/blocked geography based on certified envelope versions.
Pins outside the certified action universe are hidden or visibly blocked depending on UX context.
Changing time-budget chips triggers simulation/replanning, not local visual filtering alone.
Primary route always includes return leg and return deadline.
When RETURN_NOW is active, suppress exploration-first affordances and prioritize airport route/gate.

14. Social, Layover Crew and Presence
Layover introduces temporary real-world availability. Aggregate presence should be the default; identity and precise location are progressively disclosed only with user consent.
Visibility levels:
L0 aggregate only        “14 travelers connecting here”
L1 opt-in intent         “5 open to food”
L2 mutual discovery      profiles visible under policy
L3 crew formed           shared chat / meeting point
L4 temporary location    explicit, scoped, auto-expiring
14.1 Crew constraint solving
shared_return_by = min(member.required_return_by)

Unless an explicit split plan exists:
  member A leaves at T1
  members B/C continue until T2

Crew plan must be certified against every member branch.
No precise stranger location by default.
Crew location sharing expires on crew dissolution, airport re-entry, boarding, session expiry, or user revocation.
Traveler pins should not expose an unsafe “meet here” action without the established social/safety gate.
Shared rides require opt-in and should avoid revealing full itinerary to unrelated users.

  ↓
RETURN_NOW
  ↓

At CONNECTION_AT_RISK:

15.1 One-tap abort
Every active landside plan must expose RETURN TO AIRPORT. The action cancels optional itinerary state, marks the session RETURNING, surfaces fastest certified route, notifies relevant crew/buddy flows, preserves offline route/deadline, and records the transition in the decision ledger.
15.2 Disruption mode
CONNECTION → DELAYED → SEVERE_DELAY → OVERNIGHT
           ↘ CANCELLED → REBOOKING / RECOVERY

Disruption may expand or shrink the FreedomWindow. Recompute; do not simply append delay minutes.

Users may read/write their own layover session inputs within allowed fields.
Computed snapshots, risk, return plans and certification fields are server-controlled.

Aggregated airport intelligence must not leak raw user identifiers.

Appendix B. Example end-to-end sessions
B.1 Normal 6-hour international layover
1.  Trips detects HND connection and creates DETECTED session.
2.  Entry permission, baggage-through status and terminals resolve; session enters EVALUATING.
3.  Feasibility engine creates Snapshot 1: 214 usable minutes, LOW risk, landside allowed.
4.  Experience Compiler certifies three plans; Compass presents “Best Experience / Lowest Stress / Most Social.”
5.  User selects plan; session becomes PLAN_SELECTED then EXECUTING after airport exit checkpoint.
6.  Traffic worsens; mobility event triggers Snapshot 2 and moves latest activity departure 17 minutes earlier.
7.  OpportunityEvent is material; user receives “Leave 17 minutes earlier.”
8.  User taps Return to Airport; session becomes RETURNING.
9.  Airport re-entry checkpoint transitions to AIRPORT_REENTERED; gate context replaces exploration.
10.  Boarding completes; outcome records safe return and optional Memory/Stamp.
B.2 Unknown baggage blocks landside plan
1.  Session has a 4h45m connection but baggage mode is UNKNOWN.
2.  Value-of-information check determines baggage status can change landside eligibility.
3.  Compass asks exactly one question: “Is your checked bag tagged through to the final destination?”
4.  Until resolved, the engine returns AIRPORT_ONLY / INSUFFICIENT confidence for landside recommendations.
5.  If confirmed CHECKED_THROUGH, a new snapshot is created and landside feasibility is evaluated.
B.3 Cancellation becomes temporary community
1.  Flight cancellation event transitions affected sessions to CANCELLED.
2.  Replanner invalidates connection-specific recommendations and computes recovery context.
3.  Compass surfaces airline/airport help, hotel/transport options, and opt-in aggregate count of similarly stranded Portava travelers.
4.  Users may opt into a rescue crew by intent (hotel, taxi share, translation).
5.  No individual identity/location is exposed until mutual opt-in / crew membership.

Appendix C. Developer rules / invariants
1.  Never query a semantic substitute for a missing field and pretend it is the requested fact. Unknown is preferable to fabricated certainty.
2.  Never swallow a schema/data error and turn it into plausible empty operational state without structured logging and degraded confidence.
3.  Never let a test fixture assert impossible production joins. Live-schema/literal checks must cover safety-critical query paths.
4.  Never duplicate safety calculations across UI surfaces.
5.  Never certify a recommendation against a snapshot other than the one returned with it.
6.  Never update the active snapshot with a stale engine result; use version/CAS semantics.
7.  Never allow commercial ranking before the safety/time gate.
8.  Never keep temporary precise crew location beyond its explicit scope.
9.  Never describe cached intelligence as live.
10.  Never allow Compass prose to expand deterministic safety boundaries.
11.  Always persist reason codes and provenance for consequential decisions.
12.  Always test monotonic safety properties and actual CI schema compatibility.
13.  Always make graceful degradation truthful: null/unknown/stale are valid states.
14.  Always keep the generalized Temporal Freedom Engine free of airport-specific assumptions; use adapters.
Engineering north starA successful Layover implementation should be able to answer, deterministically and explainably: “What can this traveler safely do before the next obligation, what changed since the last answer, and what must they do now?” All Portava surfaces should agree because they are reading the same certified operational truth.
