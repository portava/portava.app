Primary invariantA Telegraph surface may display, discuss and orchestrate Portava objects, but Telegraph must never invent or silently mutate canonical truth owned by Trips, Plans, Events, Memories, Buddy, Safety, Map or other source domains.
1. Product Architecture
1.1 Product thesis
Telegraph should not be designed as a conventional DM product with travel attachments. It is the private coordination protocol that connects people, context and action across Portava.
PORTAVA CONTENT + PEOPLE + TIME + PLACE + AVAILABILITY                       ↓                   TELEGRAPH                       ↓         TALK → DECIDE → PLAN → COORDINATE                       ↓                REAL-WORLD ACTION                       ↓                    MEMORY
1.2 North-star behavior
Optimize for successful coordinated real-world actions, not message volume, streaks, time in chat or endless engagement. A conversation ending because everyone met is a successful outcome.
1.3 Core product pillars
Pillar
Definition
Talk
Reliable text, rich media, voice, GIFs, replies, reactions, seen states and safe message lifecycle.
Share
Any eligible Portava object can move through Telegraph using a safe, permission-aware share projection.
Together

3. Shared Context Rail
At the top of each conversation, show mutually relevant events, plans, Trips and related Portava objects created or joined by both sides. This is the key answer to “what are we doing together?”
3.1 Eligibility
Created by me and joined/saved/attended by the other participant.
Created by them and joined/saved/attended by me.
Both are members/participants in the same Trip, Plan, Crew, Event or booking.
Both deliberately promoted an item into a shared wishlist or “Want to Do” state.
Past shared objects remain available in the historical view only when still authorized.
3.2 Never infer mutuality from chat alone
A place that one person merely sent in a message is shared content, not a mutual plan. Promotion into the Shared Context Rail requires canonical mutual state, explicit pinning, or a shared-object rule.

4. Nearby & Available
Nearby is an opt-in social opportunity layer. Availability, presence, proximity and location sharing are separate concepts and permissions.
Hard ruleAVAILABLE ≠ ONLINE ≠ NEARBY ≠ SHARING LOCATION. Never collapse these states into one permission.
4.1 Availability primitive
type AvailabilitySignal = {  id: UUID  userId: UUID  state: 'FREE_NOW' | 'FREE_TONIGHT' | 'FREE_TODAY' | 'AVAILABLE_WINDOW' | 'IM_AROUND' | 'OPEN_TO_JOINING'  intents: AvailabilityIntent[]  startsAt: Timestamp  expiresAt: Timestamp  audiencePolicyId: UUID  proximityVisibility: 'HIDDEN' | 'NEARBY' | 'DISTANCE_BUCKET' | 'ETA_IF_MUTUAL'  geographyScope?: GeographyScope}
4.2 Nearby ranking
nearbyRank = f(  activeAvailability,  relationshipStrength,  intentCompatibility,  sharedContext,  overlappingFreedomWindow,  travelTime,  proximityBucket,  freshness,  safetyEligibility)
4.3 Privacy safeguards
Use approximate proximity or controlled distance buckets by default.
Do not allow repeated refreshes to become a movement-tracking side channel.
Exact ETA/location requires stronger mutual coordination permissions.
Availability expires automatically and revokes across Telegraph, Discovery and Compass.
Invisible mode suppresses Nearby/Bump/public availability while allowing private Map use.
Blocking is absolute and removes both parties from each other’s proximity surfaces.
Privacy zones can suppress discovery around home, lodging or user-defined sensitive places.
4.4 Who’s Around
Provide a focused surface for people, open plans and events that are actionable right now. Existing social graph should be separated from discoverable strangers. Stranger flows use safe profile preview → Wave/Request → accepted Telegraph thread; no automatic unrestricted messaging.

7. Message Lifecycle: Seen, Unsend, Edit
7.1 Delivery lifecycle
SENDING → SENT → DELIVERED → SEEN    ↘ FAILEDSENT/DELIVERED + no eligible recipient has seen    → UNSENT
7.2 Seen semantics
Seen means the message crossed the approved visibility threshold in an active foreground conversation. Push delivery, app launch or background rendering do not count as seen.
7.3 Scalable receipts
conversation_members.lastDeliveredSequenceconversation_members.lastSeenSequence
For direct chats, show Sent/Delivered/Seen. For groups, derive “Seen by N” and optionally list viewers when policy allows. Do not create permanent row-per-message-per-user receipt explosions unless a specialized audit case requires it.
7.4 Unsend-before-seen
A sender may unsend only while no eligible recipient has seen the message. In a group, one recipient seeing the message closes the unseen-unsend window for everyone. The server resolves read-vs-unsend races transactionally.
UNSEND_MESSAGE(messageId, expectedVersion)  authorize sender  lock message/conversation receipt state  assert maxRecipientSeenSequence < message.sequence  set lifecycle = UNSENT  emit message.unsent  preserve sequence tombstone internally  remove from normal retrieval/search/projections
7.5 Edit
Text edits retain an Edited marker and version history as required. Editing message prose never silently mutates a canonical Plan/Event/Trip object previously created from the message.

11. Design System & Interaction Rules
11.1 Visual character
Dark-first visual system may be used for the Telegraph concept, but components must support Portava light/dark themes.
Use restrained teal/cyan as operational emphasis; reserve stronger attention states for safety and urgent changes.
Cards should be compact and contextual. Telegraph should not visually resemble a social feed inside a chat.
Use horizontal rails only for short, high-value context sets; provide “See all” for expansion.
Message bubbles remain visually dominant once the user scrolls into the conversation.

11.3 Accessibility
Do not encode delivery/availability solely by color.
Provide reduced-motion behavior for media, GIFs and animations.
Voice/video controls require screen-reader labels and predictable hit targets.
Captions/transcripts must be optional derivatives; original media remains accessible.
Nearby/proximity labels should be understandable without map-only representation.

14. Authorization & Conversation Policy
14.1 Capability model
type ConversationCapabilities = {  canSendMessage: boolean  canCall: boolean  canCreatePlan: boolean  canShareExactLocation: boolean  canInvite: boolean  canRequestPayment: boolean  canCreateBooking: boolean  canBroadcast: boolean  canViewPreMembershipHistory: boolean  canSeeGroupReadReceipts: boolean}
Capabilities are derived server-side from membership, block state, Trip/Crew membership, booking state, age/policy, location scope, safety state and conversation type. UI renders capabilities; it does not invent authorization.
14.2 Read authorization is dynamic
Authorization must be checked both when sending and when reading because membership, revocation, source-object privacy and blocking can change after a message was created.
14.3 Group history bounds
conversation_member.visibleFromSequenceconversation_member.visibleUntilSequence
New members do not automatically receive pre-membership history. Adding a third person to a DM creates a new group; it does not expose the old DM history. Explicitly selected Plans/Places may be carried forward as new share objects.
15. Location, Proximity & Safety
15.1 Purpose-bound location
type LocationShare = {  id: UUID  ownerId: UUID  audiencePolicyId: UUID  purpose: 'MEETUP' | 'TRIP_CREW' | 'SAFE_RETURN' | 'EVENT_FIND_FRIENDS' | 'BUDDY_BOOKING'  precision: 'EXACT' | 'APPROXIMATE' | 'ARRIVAL_STATUS_ONLY'  startsAt: Timestamp  expiresAt: Timestamp  lifecycle: 'LIVE' | 'RECENT' | 'LAST_KNOWN' | 'EXPIRED'}
A meetup location grant cannot be silently reused for general Nearby discovery or future tracking. Expired location becomes inaccessible, not merely hidden in UI.
15.2 Safety mode
NORMAL → SAFETY_ATTENTION → SAFETY_EVENT
Safety mode promotes trusted contact, current status, official help, route/return, call, block/report and relevant location scope while de-prioritizing entertainment actions.
15.3 Block cascade
Blocking must cascade across direct delivery, location, presence, Nearby, Bump discovery, shared-memory resurfacing, Crew suggestions and Compass retrieval. No subsystem may independently “rediscover” a blocked relationship.
16. Media Pipeline
16.1 Media asset separation
MediaAsset != Message != MemoryMessageAttachment → MediaAssetMemory media link → MediaAssetPortava object share → source object + share projection
16.2 Progressive upload
LOCAL PREVIEW   ↓THUMBNAIL / POSTER   ↓STREAMABLE RENDITION   ↓ORIGINAL COMPLETES

17. Offline, Realtime & Multi-Device
17.1 Ordering
Require per-conversation server sequence ordering, not global ordering. Client timestamps are advisory only.
17.2 Offline commands
clientMessageIdidempotencyKeycreatedAtClientsyncState: LOCAL_ONLY | QUEUED | SENT | CONFIRMED | FAILED
Offline resend must be idempotent. Tombstones preserve sequence continuity for unsent/deleted messages. Reconnect resumes from last acknowledged conversation/event sequence.
17.3 Multi-device convergence
Seen/delivery state, message edits and canonical thread state converge server-side. Active precise location is device-specific and must not automatically transfer to a newly logged-in device.
17.4 Degraded mode
Realtime gateway failure → polling/delta fallback.
Push failure → no loss of canonical messages; push is wakeup/fallback, not consistency authority.
Translation/AI/maps failure → core messaging continues.
Low bandwidth → deprioritize typing, reactions, media preview and AI before text or safety coordination.

Telegraph search is object-aware and authorization-scoped.

“Ask this conversation” should prefer structured plans/decisions/actions over inferred prose.

29. Non-Negotiable Developer Invariants
No AI, translation, transcription, maps or push dependency in the core message-delivery path.
No exact location without explicit purpose/audience/precision/expiry authorization.
No stale location labeled live.
No private canonical Memory exposed through a Telegraph share.
No source-object revocation bypass via cached Telegraph card/search/Compass.
No direct mutation of canonical Trip/Plan/Event/Buddy terms from message prose.
No semantic ID substitution across domains.
No group-add operation that leaks prior DM history.
No silent schema failures that become plausible empty state.
No hidden client-side authorization replacing server policy.
No derived translation/transcript overwriting original content.
No automatic Memory creation from private conversation history.
No Nearby exposure merely because GPS indicates physical proximity.
Blocked relationships never reappear through Nearby, Compass, Bump or shared-memory suggestions.
Derived projections are rebuildable from canonical state + events.
