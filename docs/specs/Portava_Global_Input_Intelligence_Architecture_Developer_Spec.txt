
PORTAVA
Global Input Intelligence ArchitectureDeveloper Specification
Canonical cross-app architecture for every meaningful typed input
Typeahead · Autocomplete · Search Assistance · Intent Resolution · Smart Actions · Validation · AI Assistance
“Every meaningful Portava input should help move a user from vague intent to a valid entity, clear decision, or real-world action with as little typing as possible.”
Core rule: Anywhere the user types, Portava should intelligently assist without hijacking the user’s input.
Status: Canonical platform architecture. This is not owned by Discovery, Media, Map, Trips, Telegraph, Compass, or Create. Those surfaces consume it through a shared platform layer.

1. Product Definition
Portava Global Input Intelligence is a shared platform layer that understands the field a user is typing into, the task they are trying to complete, the entities and constraints implied by their text, the context Portava is permitted to use, and the best valid suggestion or action that should come next.
This system is larger than autocomplete. It is the typed-input control plane for Portava.
Responsibility
What it means
Understand context
Know whether the field is a city picker, caption, search box, message, Trip stop, Hidden Gem location, Compass prompt, username, etc.
Assist
Return entities, completions, actions, corrections, validations, or AI suggestions appropriate to that field.
Structure
Convert selected text into canonical entity IDs, time windows, categories, actions, and constraints.
Protect
Apply privacy, block, eligibility, trust, and location rules before suggestions reach the client.
Learn
Improve ranking from accepted/ignored suggestions and successful downstream outcomes without optimizing for typing volume.
2. Non-Negotiable Principles
One platform layer. Feature teams must not build independent autocomplete engines unless explicitly approved by architecture.
The field owns behavior; the Input Intelligence platform owns suggestion intelligence.
Canonical entities outrank AI guesses.
AI assistance never silently replaces user text.
Low-confidence interpretation must preserve raw user input.
Privacy and eligibility filtering occur before projection to the client.
Current/live suggestions must carry freshness and must never be fabricated when live state is unavailable.
Offline mode must degrade gracefully and must not present stale data as live.
Suggestions should accelerate real-world outcomes, not increase keystrokes or engagement for its own sake.
Every accepted suggestion must resolve to a valid canonical destination, structured value, or explicit user-approved action.

9. Candidate Source Hierarchy
Different fields may change weights, but the default trust order is deterministic:
1. Exact canonical Portava entity2. Strong canonical prefix / alias match3. Current task and selected-field context4. Current / upcoming Trip context5. Nearby geographic relevance6. Recent user selection7. Saved / followed / explicit relationship8. Fresh Live Intelligence relevance9. Approved external provider candidate10. Generic query completion11. AI-generated suggestion
AI must never outrank a strong canonical city, place, user, Trip, Event, Gem, or other real entity match.
10. Query and Text Normalization
Unicode normalization and safe whitespace folding.
Case-insensitive matching.
Diacritic-insensitive matching while preserving display spelling.
Alias resolution and known abbreviations.
Common misspelling tolerance.
Local-language and English-name variants.
Transliteration where supported.
Punctuation and emoji handling appropriate to field context.
Phone/keyboard typo tolerance where confidence is sufficient.
Never normalize stored canonical display names destructively.
Examples:  da nang  → Đà Nẵng  danang   → Đà Nẵng  hcmc     → Ho Chi Minh City  saigon   → Ho Chi Minh City  phu qouc → Phu Quoc

15. Context-Aware Ranking
The same text should produce different rankings depending on the active field and task.
SuggestionScore =    ExactMatch  + PrefixMatch  + ContextFit  + GeographicFit  + TripFit  + TemporalFit  + RelationshipFit  + Freshness  + PriorSelection  + TrustConfidence  + Diversity  - PrivacyRisk  - Staleness  - Ambiguity  - SpamRisk
16. Context Carryover and Session State
Inputs within the same task should share permitted context. A field must not behave as though it exists in isolation.
Trip destination = Bangkok        ↓Trip stop place picker → Bangkok places firstEvent location inside Trip → Bangkok candidates firstCompass prompt → Bangkok Trip context attachedHidden Gem lookup → Bangkok Gems prioritized
Context carryover must be bounded to the active task/session and must not silently change unrelated persistent preferences.
17. Cross-Field Dependency Graph
When one structured field is selected, dependent fields may use it as a constraint or prefill source.
Venue = Sky36   ↓City = Da NangCountry = VietnamCoordinates = canonical Place coordinatesTimezone = Asia/Ho_Chi_Minh
Autofilled fields must remain visible, attributable, and editable. No invisible field mutation.

20. Constraint-Aware Suggestions
Relevance is not enough. Before ranking, the system should remove or demote options that are infeasible or inappropriate for the field.
Closed or unavailable where current operating status is relevant.
Outside Trip date/time window.
Outside selected city/area where the field is constrained.
Age, trust, membership, role, or invite restrictions.
Unavailable Buddy category or required safety/payment gate.
Blocked/private/ineligible people or content.
Protected or sensitive locations whose exact position cannot be surfaced.
Stale live states beyond allowed freshness.
Duplicate Place/Gem/Event candidates when creation mode should resolve existing records first.

25. Voice and Dictation

26. Mention, Hashtag, and Entity Insertion

29. Privacy and Eligibility Gateway
No suggestion is returned merely because it matched text. Viewer eligibility is resolved first.
Blocked users and blocked relationships suppressed.
Private Trips/Events/Plans excluded unless viewer is eligible.
Private captions/tags/metadata never enter public suggestion indexes.
Precise private location never leaked through autocomplete.
Presence/location inference cannot be exposed beyond current authorization.
Memory-based suggestions remain owner-scoped unless deliberately shared.
Sensitive location and protected-place rules applied before projection.
AI must receive only the minimum permitted structured context needed for the requested assistance.
30. Conflict Resolution Precedence
Canonical identity    > verified/current authoritative state    > current eligible Portava community state    > approved provider state    > cached historical state    > user raw input    > AI guess
This order is not a universal ranking score; it is a conflict-resolution rule for factual identity/state. If uncertainty remains, show disambiguation rather than inventing resolution.
31. Freshness and Live Intelligence
Live suggestions may enhance autocomplete, but they remain projections of the Live Intelligence system.

35. Selection Memory and Personalization
The engine may learn from repeated explicit selections, not inferred private facts.
Recently selected cities/places/users.
Frequently selected abbreviations mapped to the same canonical entity for that user.
Saved and Trip-related entities.
Previously successful query completions.
Context-specific selection patterns.
Example: repeated “BKK” → Bangkok selection can improve that user’s future rank without changing the canonical city name.
36. Anti-Spam and Manipulation Controls
Keyword stuffing resistance in business/Buddy/user descriptions.
Alias abuse detection.
Impersonation protections for people and businesses.
Duplicate entity suppression.
Rate limits on suggestion-affecting submissions.
No paid boost into factual confidence or canonical identity priority.
Provider neutrality: do not favor a source merely because it was integrated first.
37. Empty and No-Match States
No exact Place found.[Search instead][Drop a pin][Add a new Place][Ask Compass][Search nearby]
Available fallback actions are context-dependent. A city picker should not offer “create city”; a Hidden Gem/location flow may offer map-point or new-entity creation under policy.
38. Failure Fallback Ladder
Canonical Portava results        ↓Cached canonical results        ↓Approved provider candidates        ↓Local index / recent history        ↓Raw query submission
Provider failure must not collapse the input UI. Preserve canonical records and valid local fallbacks.

45. Learning Loop
Suggestion shown    ↓Selected / ignored / edited    ↓Did downstream task succeed?    ↓Rank calibration    ↓Context-specific improvement
Optimize for successful entity resolution, task completion, appropriate action, and useful real-world outcome. Do not optimize merely for suggestion acceptance rate.
46. Accessibility
Screen readers announce field purpose, suggestion count, active suggestion, and selection result.
Arrow-key and keyboard navigation on web/desktop.
VoiceOver/TalkBack focus management on mobile.
No suggestion overlay trapped behind software keyboard.
Dynamic type and large text support.
High contrast and non-color-only state indicators.
Reduced-motion support.
Clear loading/error/empty states.
Undo or edit path after replacement.
47. Security and Abuse Boundaries
Do not expose internal IDs unless required by client contract.
Rate-limit high-volume prefix enumeration where it can reveal private entity existence.
Protect recipient/user search from account enumeration abuse.
Apply authentication and viewer scope before private entity lookup.
Sanitize pasted URLs and untrusted text before rendering.
AI-assisted paths must not bypass validation, moderation, or authorization.
All action suggestions use the same authorization gate as the target action itself.
48. Versioning and Compatibility
Version field-policy registry independently from app releases.
Version suggestion response schema.
Preserve backward compatibility for active mobile versions.
Feature-capability handshake for suggestion types unsupported by older clients.
Allow server-side policy updates without requiring a client release where safe.
Never change canonical entity semantics through ranking-only configuration.

52. Feature-Team Adoption Rule
Do not build a new autocomplete, predictive text system, recent-search list, entity typeahead, suggestion dropdown, AI writing helper, or input-specific resolver inside a feature until the Global Input Intelligence layer has been evaluated first.
New fields are added by registering a policy and consuming shared primitives. Feature-specific behavior should be configuration or a narrowly scoped resolver extension, not a second architecture.

58. Final Architecture Principle
TEXT  ↓MEANING  ↓ENTITY / CONSTRAINT / INTENT  ↓VALID SUGGESTION  ↓USER CHOICE  ↓ACTION  ↓REAL-WORLD OUTCOME
Portava should not merely autocomplete words. It should progressively convert human intent into canonical entities, constraints, actions, and real-world plans while preserving user control, privacy, and uncertainty.
