
PORTAVA
Trips Development Architecture
Developer Specification v4
Trip Kernel • Journey Graph • Coordination • Temporal Freedom • Live Intelligence • Safety • Memory
Engineering goal: make Trips the canonical operating system for a journey — before, during, and after travel.
Architecture target: mobile + API + Supabase/Postgres + Compass orchestration + event/projection infrastructure

1. Executive Architecture
Trips is not an itinerary list. It is Portava’s canonical journey runtime: the domain that coordinates people, commitments, plans, places, transport, bookings, live conditions, social presence, safety state, and outcomes for a defined journey.
Primary invariant
A Trip surface may present or orchestrate plans, but all consequential state changes must pass through the Trip Kernel. No Map, Compass, Telegraph, Discovery, Buddy, or UI component may independently invent canonical trip state.

2.2 Aggregate boundary
The Trip aggregate owns ordering and invariants that require a coherent version. Large read models are projections, not transactionally embedded payloads. High-volume ephemeral signals (location samples, crowd intel, chat messages) remain in their specialist stores and are referenced by stable IDs.
2.3 Canonical IDs
Identity rule
Never substitute one domain ID for another because names or coordinates look similar. All cross-domain linkage uses explicit foreign keys or reconciliation records. Place, hidden-gem, event, booking, buddy, and flight IDs remain distinct until a canonical bridge exists.

6. Authorization, RLS, and Policy Layer
6.1 Roles are not permissions
Host, co-host, member, guest, local, and buddy are coarse roles. Capabilities are derived from role + trip policy + plan membership + privacy scope. Application code calls policy functions rather than scattering host checks.
canViewTrip(actor, trip)canInviteParticipant(actor, trip)canEditTrip(actor, trip)canCreatePlan(actor, trip)canModifyPlan(actor, plan)canManageBooking(actor, trip)canSeePresence(actor, subject, trip)canSeePreciseLocation(actor, subject, trip)canManageSafety(actor, trip)
6.2 RLS principles
Default deny client writes to sensitive coordination/safety tables unless an explicit safe client path exists.
Membership does not imply precise location access, payment access, document access, or safety access.
Service-role mutations still pass application authorization and command validation; service role is not business authorization.
Policy tests must include negative assertions for anonymous, non-member, removed member, guest, host, and service-facing paths.
6.3 Privacy scopes
PRIVATE | SELECTED_PARTICIPANTS | CREW | FRIENDS_NEARBY | TRIP | PUBLIC
Public Trip content must not leak lodging detail, exact private location, future absence from home, safety state, or unconsented participant data.

7. Temporal and Spatial Consistency Engine
7.1 Commitment model
Commitment {  startsAt  requiredArrivalAt  placeId  latenessTolerance  prepDuration  flexibility  confidence}
7.2 Core invariant
previous.end+ route(previous.place, next.place, future_departure_time)+ required_buffer(next)<= next.requiredArrivalAt
Confirmed timelines may contain known conflicts only when explicitly overridden and visibly marked. A conflict is not silently rendered as a normal itinerary.
7.3 Freedom windows
FreedomWindow {  beginsAt  endsAt  origin  requiredDestination  participants  hardConstraints[]  confidence}
Trips queries the Temporal Freedom Engine for gaps between commitments. Discovery, Compass, Saved Ideas, and Buddy matching consume these windows rather than independently calculating “free time.”

8. Goals, Decisions, Readiness, and Risk
8.1 Goal graph
Trip goals capture why the journey exists and prevent optimization around generic engagement. Goals may be personal or shared and can be weighted without forcing every participant to share the same priorities.

9. Collaborative Coordination Model
9.1 Attendance
PlanScope: ALL_CREW | OPTIONAL | SUBGROUP | SOLOAttendance: INTERESTED | GOING | MAYBE | CANT_GO | LEFT
Group Trips should not assume every plan applies to every participant. Attendance is an explicit relation so downstream transport, reservation, meeting-point, and budget calculations use the actual party.
9.2 Subgroups
Temporary subgroups allow crews to split and later recombine without forking the entire Trip. A subgroup can own a meetup, shared transport, and temporary presence sharing while the parent Trip remains canonical.
9.3 Proposal governance
TripProposal {  type  proposedBy  affectedObjects[]  rationale  impactSummary  decisionRule: HOST | MAJORITY | UNANIMOUS | ANYONE  status  expiresAt}
Important shared mutations should be proposed when policy requires consensus. Compass may create a proposal, but cannot silently mutate other participants’ commitments.
9.4 Impact preview
Before a proposal that changes a confirmed plan is accepted, compute downstream impact: affected reservations, transport, participants, commitment conflicts, cancellation costs, and safety/return implications.

10. Presence, Location, and Crew State
10.1 Presence is contextual, not “online”
AVAILABLE | FREE | GETTING_READY | TRANSITING | AT_PLAN | RESTING | RETURNING | OFFLINE
Presence communicates real-world availability without requiring continuous exact GPS. Every presence row carries observed_at, expires_at, source, confidence, and visibility.
10.2 Location freshness
LIVE | RECENT | LAST_KNOWN | OFFLINE
The Trip Map must never draw a stale location as if it were current. Marker visual treatment and accessible text must expose freshness. Last-known data may remain useful but is not live truth.
10.3 Adaptive sensing
Use geofences, significant location changes, navigation callbacks, semantic checkpoints, and explicit user actions before constant GPS. Increase sensing frequency only when execution/safety requires it. Battery and privacy are system constraints.
10.4 Offline Locate My Friends integration
At large events or degraded connectivity, Trip Crew can consume the separate proximity/peer-relay subsystem: cached event maps, last-known positions, opt-in Bluetooth proximity, meeting checkpoints, and temporary relay metadata. This must not create covert persistent tracking.

12. Compass Trip Orchestration Contract
12.1 Tool surface

12.2 Hard boundary
Compass authority
Compass may explain, compose, compare, ask high-value clarifying questions, and propose actions. It may not bypass authorization, invent canonical flight/booking/place facts, relax safety constraints, expand certified freedom windows, or mutate shared commitments without the command/policy path.

12.3 Minimum-question planning
Before asking the traveler, calculate value-of-information. Ask only for unknown facts capable of materially changing feasibility, authorization, cost, or recommendation quality. Known low-impact uncertainty remains represented as uncertainty rather than becoming questionnaire friction.
12.4 Graceful AI failure
Trips must remain operational without Compass. Today, commitments, route chains, confirmed plans, crew state, safety state, and notifications are deterministic services/projections; AI is not a safety dependency.

14. Map and Route Architecture
14.1 Trip Map projection
TripMapProjection {  stage  hotel/private anchors (access controlled)  active plans  confirmed commitments  saved ideas  crew presence summaries  route chains  meetup points  live opportunities  safety/logistics points  generatedAt  sourceTripVersion}
14.2 Route chains
Trips optimizes sequences, not isolated origin/destination pairs. Route chains carry expected departure/arrival, future-time traffic/transit assumptions, cost, party size, reliability, and fallback route references.
Hotel → Dinner → Bar → Club → Hotel
14.3 Smart meeting point service
Meeting-point computation minimizes group burden subject to next commitments, accessibility, party size, venue suitability, privacy policy, and transport reliability. The service returns explanation and alternative candidates rather than a magic coordinate.
14.4 Map safety
Sensitive anchors such as hotel/private lodging must never be included in public or broad social projections. Traveler pins obey presence visibility and freshness contracts. Clusters and aggregate counts may be used where exact identity/location is unnecessary.

15. Transport, Booking, and External References
15.1 Transport segment
TransportSegment {  mode  fromPlaceId  toPlaceId  plannedDeparture  plannedArrival  state: PLANNED | BOOKED | WAITING | IN_PROGRESS | COMPLETED | DISRUPTED  providerRef?  partySize  reliability}
15.2 Booking reference boundary
Trips stores booking references and operational facts needed for coordination, not payment credentials. Booking ownership remains with the booking/provider domain. Cancellation/refund policies are imported as versioned facts and treated with provenance/confidence.
15.3 Invalidation semantics
When replanning invalidates a booked activity, the planner must return explicit side effects: booking at risk, cancellation deadline, potential cost, affected participants, and required user confirmation. Automatic replanning may not silently cancel purchases.
15.4 Compensating actions
Booking/reservation history is append-only operational truth: confirmed then cancelled, not confirmed row deleted. Compensation is represented as a new state/event so replay remains accurate.

17. Disruption, Safe Return, and Rescue
17.1 Trip health
HEALTHY → ATTENTION → AT_RISK → DISRUPTED
Health is a summary projection. It does not replace concrete risks/reason codes.
17.2 Disruption priority switch
NORMAL:          discovery / execution / socialAT_RISK:         logistics / affected commitments / recoverySAFETY_EVENT:    safety / official help / location coordination
Commercial recommendations and entertainment discovery are suppressed when a severe operational or safety state requires the user’s attention.
17.3 Trip Rescue
A rescue entry point routes to typed problems such as missed transport, hotel issue, lost crew, no ride, travel-document issue, stranded traveler, or emergency assistance. Compass can organize context but must escalate to airline, airport, embassy/consulate, local emergency, or human support where appropriate.
17.4 Safe Return integration
Safe Return can attach to solo, subgroup, or full-crew execution contexts. Status sharing is opt-in, purpose-limited, and time-limited. It exposes operational states such as RETURNING/ARRIVED/NEEDS_HELP rather than unnecessary continuous location.

18. Offline, Sync, and Multi-Device
18.1 Local cache
The mobile client stores a signed/versioned offline bundle containing next commitments, active plan, selected route, meeting points, critical addresses, cached map tiles where permitted, and the most recent certified context. Stale/live-unavailable must be visible.

20. Memory, Passport, and Post-Trip Lifecycle
20.1 Outcome-first projection
Operational logs do not become permanent memory wholesale. Durable post-trip projections are based on meaningful outcomes: places visited, activities completed, people intentionally associated, stamps, media, milestones, and user-approved story elements.
20.2 Trip closeout
COMPLETED  → stop/expire temporary presence  → dissolve temporary crews where appropriate  → reconcile uncertain plan outcomes  → close operational decision tasks  → preserve decision/audit evidence per policy  → project Passport/Memory candidates  → archive rebuildable operational projections
20.3 Minimal reconciliation
When evidence is incomplete, ask only the smallest useful post-trip question set. Example: “Did you make it to Hoi An?” instead of forcing the user to mark every plan manually.
20.4 Trip-specific vs durable preference
“We avoided seafood on this trip” is contextual. It must not automatically become a permanent user preference. Durable preference projection requires the separate memory inference policy and confidence/evidence thresholds.

22. Snapshots, Replay, Simulation, and CI
22.1 Snapshot contract
TripSnapshot {  tripId  aggregateVersion  lifecycleState  stageId  activePlanId?  nextCommitmentId?  freeWindowSummary  crewSummary  riskSummary  sourceRefs  engineVersions  createdAt}
22.2 Deterministic replay
Engineering can replay a Trip from a snapshot plus ordered events and compare resulting canonical/projection state. Event payloads are schema-versioned. Migration adapters are deterministic and covered by fixtures.
22.3 Decision-diff CI
Planner/coordination changes run against historical or synthetic Trip scenarios and report changed decisions, increased/decreased conservatism, new conflicts, and unexplained large diffs. Safety/authorization invariants block merge regardless of product experiment.
22.4 Property invariants
Earlier hard commitment cannot increase the preceding certified free window.
Closed-before-arrival activity cannot remain executable.
Removed participant cannot receive future precise trip presence through that Trip.
Unknown place identity cannot be silently treated as a canonical place match.
Projection sourceTripVersion may never exceed canonical aggregate version.
Duplicate command with the same idempotency key cannot produce duplicate state transition.

24. Migration and Rollout Plan
Phase 0 — Inventory and compatibility
Map the existing Trip tables/routes/services to the new kernel. Freeze semantic drift by documenting current write paths, direct table mutations, stage/plan types, membership logic, Map/Compass dependencies, and existing events. Do not big-bang rewrite.
Phase 1 — Kernel foundation
Add trip versioning, command service, policy layer, idempotency, event/outbox tables.
Introduce canonical Trip/Stage/Plan/Commitment contracts with compatibility adapters.
Ratchet direct writes: new code must use commands; legacy paths are enumerated and reduced.
Phase 2 — Today + temporal consistency
Build TripTodayProjection, commitments, FreedomWindow integration, temporal/spatial conflict detection.
Wire Compass read tools to canonical projections; AI cannot mutate directly.
Phase 3 — Crew coordination
Attendance, subgroups, presence TTL/freshness, proposals/governance, smart meetup service.
Phase 4 — World intelligence + opportunity
Trip Pulse, Opportunity Events, Experience Compiler, route-chain optimization, event-driven replan.
Phase 5 — resilience and lifecycle
Offline operation queue, deterministic replay, closeout, Memory/Passport projections, long-stay support.
Phase 6 — rollout certification
Enable by scenario/feature capability after invariant/replay certification. Product features may be enabled in pre-launch environments, but safety, security, privacy, cost, and irreversible-action gates remain independent controls.

25. Engineering Definition of Done
Trips vNext is architecturally complete when the following are true:
One typed Trip Kernel owns consequential canonical writes through commands.
Every accepted command is authorized, validated, idempotent, version-aware, audited, and emits a domain event.
Map, Compass, Discovery, Telegraph, Safety, Buddy, Passport, and Memory consume explicit Trip projections/contracts rather than duplicating Trip semantics.
Confirmed itineraries cannot silently contain impossible temporal/spatial relationships.
Presence and exact location are purpose-limited, privacy-scoped, freshness-labeled, and automatically expire.
Group changes support impact preview/governance when other participants are affected.
Offline writes reconcile without destructive last-write-wins behavior.
Nested layovers and multi-city stages fit the same journey graph.
Trip state can be replayed and planner changes can be decision-diffed in CI.
Post-trip operational data expires/projects cleanly into durable outcomes without over-persisting sensitive/transient state.
Final architecture principle
Trips is the Portava real-world coordination protocol. New capabilities should integrate by consuming Trip Context, issuing Trip Commands where appropriate, emitting/consuming typed events, and projecting outcomes — not by adding another isolated itinerary feature.
