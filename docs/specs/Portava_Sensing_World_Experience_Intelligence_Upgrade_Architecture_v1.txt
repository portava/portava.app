
PORTAVA
Sensing + World / Experience Intelligence
Upgrade Architecture for Developers
UPGRADE, DO NOT REBUILD
This design extends Portava's existing intelligence, map, discovery, wall, Compass, Trips, Telegraph, Memories, safety, and projection infrastructure. Existing canonical tables, lifecycle states, RLS, outbox/event patterns, feature gates, projections, and proven production paths are to be reused wherever they already satisfy the contract.

Do not introduce a second lifecycle, a second place identity, a second social presence model, or a second intelligence truth store merely because the new feature needs richer signals.

2. Product Thesis
Portava should learn about places, crowds and experiences from many small privacy-reduced contributions without building a permanent movement history of individuals.
DEVICE SIGNALS   ↓PRIVACY-REDUCED CONTRIBUTIONS   ↓PRESENCE / FLOW / CROWD / VIBE   ↓WORLD + EXPERIENCE STATE   ↓FORECAST / OPPORTUNITY / SAFETY EVIDENCE   ↓MAP · DISCOVERY · WALL · COMPASS · TRIPS · LAYOVER · TELEGRAPH   ↓EXPERIENCE SESSION   ↓OUTCOME / MEMORY / CALIBRATION
Hard semantic separations:
Busy ≠ good.
Crowded ≠ unsafe.
Rapid movement ≠ dancing.
Inference ≠ observation.
Prediction ≠ current truth.
No coverage ≠ quiet.
User dislike ≠ bad venue.
One device ≠ a crowd.
Promotional claim ≠ observed reality.
World anomaly ≠ safety incident.
3. Privacy and Identity Architecture
Encryption is required but is not sufficient. The World Intelligence path should avoid receiving permanent identity-linked raw signals whenever possible. Social location features may require identity; intelligence contribution does not.
                   DEVICE LOCATION / MOTION                           │             ┌─────────────┴─────────────┐             ↓                           ↓      SOCIAL / PERSONAL             WORLD INTELLIGENCE      purpose-specific              privacy-reduced      identity may exist            no permanent user FK             │                           │      Trip / Friends / Buddy        on-device preprocessing             │                           ↓      separate policy              short-lived credential                                         ↓                                rotating contribution ID                                         ↓                                      ingest                                         ↓                              privacy / cohort gate                                         ↓                                    aggregate
Required security properties:
TLS in transit and encrypted storage at rest.
Short-lived rotating contribution identifiers; no stable anonymous identifier that becomes a tracking identity.
World-intelligence contribution records should not carry a permanent profiles.id / account user_id foreign key unless a narrowly justified, reviewed security requirement proves it necessary.
Separate contribution eligibility/authentication from signal ingest where practical: eligibility proves an authorized participating device; ingest receives an opaque short-lived credential.
Raw precise location should be reduced on-device or inside a narrow trusted boundary as early as practical.
Sensitive-location suppression, rare-path suppression, cohort thresholds, anti-differencing controls and minimum independence requirements.
Purpose-scoped authorization: collect, retain, aggregate, infer, personalize, surface and share are distinct permissions/policies.
Raw contribution retention is short; aggregated/de-identified state may live longer according to explicit policy.
Social location data never silently becomes anonymous crowd intelligence, and anonymous crowd contributions never silently become social location.
4. Sensing System Architecture
4.1 Device sensing boundary
The device is the first privacy boundary. Prefer feature extraction over uploading raw continuous streams.
RAW DEVICE INPUTS (where OS permission and policy allow)- location- motion / accelerometer-derived features- speed / heading- dwell / transition timing- optional proximity primitives- optional coarse acoustic energy/rhythm ONLY under separate explicit permission              ↓ ON DEVICENORMALIZED SIGNAL FEATURES- spatial bucket / canonical-place candidate- temporal bucket- movement_state- motion_energy- periodicity- dwell_bucket- arrival / departure transition- transport-mode likelihood- confidence / sensor health
4.2 Contribution session
Use the existing consent / feature architecture where possible, but introduce a canonical contribution-session contract if no equivalent exists. It should represent authorization and sampling policy, not world truth.
IntelligenceContributionSession- session_id- opaque / rotating contribution credential- purpose_scopes- foreground_or_background- precision_ceiling- sampling_policy- retention_policy- privacy_budget- starts_at- expires_at- revoked_at?- client_capability/version
Do not add this table blindly. First search for existing route-flow contribution consent, location consent, session or device authorization structures and extend/reconcile rather than duplicate.
4.3 Signal ingest
DEVICE  ↓Contribution Eligibility / Credential  ↓Signal Ingest API  ↓Schema validation  ↓Replay / idempotency protection  ↓Precision reduction / canonical-place or zone assignment  ↓Privacy eligibility  ↓Short-lived contribution store  ↓Aggregation
Ingest must fail explicitly on schema/permission/infrastructure failure; never return a plausible empty world.
Rate-limit and anti-replay per credential/device security boundary.
Reject impossible timestamps, malformed precision, invalid purpose scopes and stale credentials.
Do not put precise GPS in canonical event payloads. Use canonical IDs, coarse references and privacy-reduced derivatives.
4.4 Aggregation and independence
Portava must reason about independent evidence, not raw device count. Correlated devices moving together can overstate crowd confidence.
CONTRIBUTIONS   ↓correlation / independence grouping   ↓cohort threshold   ↓spatial + temporal aggregation   ↓coverage estimate   ↓aggregate observation
One person/device never becomes 'crowd'.
A Trip crew, tour group, bus or duplicated devices should not necessarily count as independent confirmations.
Track coverage separately from estimated activity.
Aggregate flow publication must suppress rare origin→destination paths.

Feature clients and React components must not independently calculate crowd, vibe, safety, opportunity, experience value or world-change state.
7. Required Tweaks: Map
Keep current Map layer census and fallback behavior for compatibility; do not rewrite the Map gateway.
Add server-built ExperienceState to place/event Map projections rather than separate overlapping vibe pins.
Promote world_pulse into meaningful transient world-change projections: heating up, forming, moving, clearing, unexpected activity, event spillover, traveler surge.
Render crowd_flow / traveler_flow primarily as privacy-safe directional geometry rather than ordinary pins.
Add TemporaryWorldObject only if no existing canonical temporary-object contract exists; do not fake permanent Place rows for transient clusters.
Add semantic zoom: city→neighborhood/world dynamics; district→hotspots/flows; place→vibe/crowd/queue.
Add truth/freshness/coverage metadata and visually distinguish predicted from observed state.
Add display resolver / clutter budget so safety, mode, zoom, user intent and relevance decide what renders.
Safety constraints outrank opportunity/vibe. A dangerous place must never simultaneously be promoted as 'best move now.'
Map remains a projection consumer, never owner of world truth.
8. Required Tweaks: Discovery
Discovery becomes 'what is worth considering now or soon,' not merely static relevance/popularity.
Rank using live ExperienceState, forecast, travel time, friction, compatibility, freshness, safety and Opportunity value.
Keep search/retrieval truth separate from recommendation ranking; a quiet venue still exists in search.
Introduce server-built DiscoveryCandidate / projection with why-now, why-for-user, confidence, freshness and truth class.
Strengthen Hidden Gems with behavioral evidence such as stickiness, conversion, organic arrivals and repeat activity, but create candidates—not automatic canonical gems.
Support intent modes using the same shared intelligence: Right Now, Tonight, Explore, Quiet, Social, High Energy, Nearby, Trip.
9. Required Tweaks: Wall
Wall consumes meaningful state transitions, not repeated snapshots of unchanged state.
Examples: place warming→building, event starting, saved place peaking, crowd shift, hidden gem emerging, Trip opportunity opening, safety notice activation.
Add a server-built WallMoment / equivalent projection with subject, transition, occurred_at, relevance window, reason, truth class, freshness and expiry.
Preserve Wall as chronological/current-life architecture. Do not turn it into an opaque engagement-maximizing ranking feed.
Live Now strip should consume current projections; chronological Wall records transitions/history. Do not duplicate both.
Personalization controls whether a canonical world event matters to a user; it must not rewrite the world event.
10. Required Tweaks: Compass and Home
Compass becomes the primary decision consumer:
USER CONTEXT+ WORLD STATE+ EXPERIENCE STATE+ FORECAST+ TRIP / LAYOVER+ TIME / FRICTION+ SAFETY+ CURRENT EXPERIENCE        ↓DECISIONGO NOW · GO SOON · WAIT · STAY · SWITCH · SKIP · RETURN
Compass must ground natural-language claims in structured truth. Low-confidence dance_likelihood cannot become 'everyone is dancing.'
Current Experience value introduces switching cost so Compass does not constantly tell users to abandon a good experience.
Home should consume a UserNowProjection / equivalent assembled server-side rather than query many domains independently.
Home is the answer to 'what matters right now'; Compass is 'what should I do about it?'
11. Required Tweaks: Trips and Layover
Add TripWorldContext / equivalent projection containing current world state, nearby opportunities, disruptions, ExperienceSessions and crew context.
World Intelligence may propose Trip changes; it may not directly mutate canonical Trip plans. Consequential changes still pass through Trip Kernel/command path.
Layover Temporal Freedom Engine should intersect feasibility with live Experience value, forecast, friction and safe-return constraints.
Use peak interception: can the user reach the experience before its useful window decays?
12. Required Tweaks: Telegraph
Share canonical references to ExperienceState / Opportunity / WorldMoment / SafetyNotice rather than copying stale prose.
Shared live objects may indicate that state changed since sharing.
Telegraph coordination can consume live intelligence to build Plans/Rendezvous, but must not expose anonymous intelligence contributors.
Nearby & Available remains separate from anonymous contribution sensing.
13. Required Tweaks: Memories and Passport
Raw passive sensing must never automatically become Memory.
Bridge through ExperienceSession and outcome/significance eligibility.
Passport consumes meaningful visited/experienced outcomes—not raw movement logs.
World Intelligence, personal Memory and social location remain separate retention/permission domains.
14. Required Tweaks: Places, Events and Hidden Gems
Do not bloat durable places rows with current_vibe/current_crowd/current_energy fields; keep dynamic state in projections.
Events may expose runtime inferred/official phases, but source classes and truth classes remain distinct.
Temporary activity must not be forced onto nearest place ID when ownership is unknown.
HiddenGemCandidate should be distinct from canonical Hidden Gem approval if the repo already separates candidates/review.
15. Required Tweaks: Search, Create and Attention
Search can use live state as ranking context while preserving lexical/entity correctness.
Autocomplete may surface live/inferred suggestions but must label them as current intelligence, not durable metadata.
Create content and structured intelligence observation must be separate commands. A post saying 'dead' cannot directly mutate CrowdState.
Attention Engine is mandatory: World changes route through relevance, novelty, urgency, half-life, user availability, interruption cost and attention budget before NOTIFY / WALL / SILENT / IGNORE.
16. Required Tweaks: Safety and Trust
WORLD INTELLIGENCE    ↓ evidence / anomalySAFETY CANDIDATE    ↓existing safety policy / review / authority    ↓CANONICAL SAFETY ASSERTION
World anomalies never auto-promote to danger.
Crowded remains ordinary intelligence unless safety-specific evidence/policy authorizes unsafe density.
Do not weaken the existing safety review/privacy path.
Source reliability / signal reliability are not the same as person Trust Score.
Do not score a user as trustworthy because their passive movement looks 'normal.'
17. Required Tweaks: Presence, Rent-a-Buddy, Locate My Friends
Promote a shared platform Presence architecture, but keep privacy classes distinct: private device presence, aggregate intelligence presence, social presence, Trip crew, Buddy, public discovery.
Reuse low-level sensor/proximity infrastructure where possible, not consent/policy semantics.
Locate My Friends may use identity/peer relay/checkpoints under group permissions; anonymous World Intelligence may not reverse-resolve contributors.
RAB may consume public/aggregate area intelligence and authorized Buddy presence, but never infer or expose individual anonymous contributors.

20. Failure Semantics and Invariants
Schema/permission/infrastructure failure ≠ no activity.
Insufficient coverage ≠ quiet.
Expired/stale state ≠ current.
Prediction ≠ observation.
Inference confidence may only decrease through conflict unless new evidence supports an increase.
No product surface may fabricate world state to make UI look complete.
Safety suppression/constraint must win over opportunity promotion.
Anonymous intelligence may not be reverse-linked to a Portava account.
Existing legacy fallbacks must not be suppressed merely because a new gateway/projection is partially enabled.
All consequential canonical mutations use existing command/service/RLS patterns, not client direct writes.
21. Incremental Implementation Sequence
S0 — Audit / mapping: Inventory current consent, route-flow contribution, device/session, map projection, intel observations/claims/snapshots, wall, discovery, Compass, schedulers, RLS, outbox and feature flags. Produce reuse map; no mutation.
S1 — Privacy contract: Define purpose scopes, contribution credential/session, rotating IDs, retention, precision ladder, sensitive locations, cohort thresholds and revocation using existing policy primitives.
S2 — Ingest + aggregation: Add minimal privacy-reduced ingest and aggregate/coverage path. Certify anti-replay, no permanent user FK, TTL, unknown-vs-quiet, and failure observability.
S3 — Presence / Crowd / Flow: Wire server-built states through existing intelligence projection architecture. Do not yet add vibe.
S4 — Vibe / ExperienceState: Add inference with explicit truth metadata; mutation/property test rapid-movement≠dancing and no-coverage≠quiet.
S5 — Map upgrade: Add ExperienceState, flow geometry, WorldMoment, semantic zoom and display resolver without replacing legacy map gateway/fallback.
S6 — Discovery + Wall: Server-built DiscoveryCandidate and WallMoment projections; certify no client truth duplication.
S7 — Compass + Home: Decision grounding, current-experience switching cost, UserNowProjection.
S8 — Trips / Layover / Telegraph: Consume existing world/experience contracts; preserve each domain's canonical mutation owner.
S9 — ExperienceSession + outcome: Close recommendation→experience→outcome loop; keep Memory eligibility separate.
S10 — Remaining consumers: Search/Create/Notifications/RAB/Passport/Hidden Gems/Event runtime projections.
S11 — Shadow / calibration: Run forecast/vibe in shadow mode, compare against later evidence, track version lineage and model calibration before aggressive surfacing.
22. PR / Repo Safety Strategy
One architectural responsibility per PR where practical.
Do not combine unrelated schema cleanup, Trust work, Safety work or legacy refactors into sensing PRs.
Prefer additive migrations with postconditions; no destructive migration unless separately reviewed.
Every new server contract gets positive tests, RLS/authz negatives, stale/unknown cases and malformed input cases.
Use static ratchets for forbidden direct writes, identity joins or bad literals where helpful.
Mutation-prove critical invariants: no permanent identity link, no single-device crowd, no prediction-as-observation, no anomaly-as-safety, no client-computed vibe.
Feature flags should allow shadow/read-only rollout. Do not claim LIVE until highest-level gate, schema, policy, scheduler, data dependency and production path are satisfied.
