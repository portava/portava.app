# Portava recording stamps

A stamp identifies one video submitted through Portava’s recording flow and the Story or post where its author published it. The public mark has an issuer-generated ID. Opening the mark checks its current publication and stored video. Use “Portava recording stamp” in the interface. Its assurance covers upload integrity and publication binding. Location, the depicted scene, camera hardware, and the person behind the camera are outside that assurance. An independently modified client with valid account credentials can submit video bytes to the recording protocol.

The camera requests a challenge from `POST /api/capture-stamps/sessions` before recording. The challenge lasts 30 minutes and belongs to the authenticated account. The app keeps it with the selected recording and sends it in `X-Portava-Capture-Token` on the existing raw video upload when the author selects the stamp. The upload server validates the container, removes location metadata, and hashes the exact bytes it stores in a protected object path. A retry must submit the same bytes.

After publication, `POST /api/capture-stamps/issue` accepts the challenge, publication ID and type (`story` or `post`). The database checks the owner, attachment, current publication, and storage generation, then creates the public stamp ID. Repeating the request for the same publication returns that ID. A second target, different owner, or reused recording digest is refused. Account deletion cascades the receipt. Pending challenges expire and the issuer prunes abandoned rows on subsequent session creation.

The viewer calls `GET /api/capture-stamps/:type/:id`. A hidden, expired, removed, detached, or replaced original yields no mark. The viewer must satisfy the publication’s audience rules and current byte authorization. The public response contains the stamp ID, display code, target, issue time and stamp kind. Content reactions and Passport achievement awards are separate existing mechanisms and grant no recording verification or travel-presence credit.

Migration `4019_recording_capture_stamps.sql` installs the service-only issuer commands and restrictive storage policies. The local `test:recording-capture-native` gate runs against PostgreSQL 17 and exercises retry/concurrency, tampering, substitution, expiry and storage access. Existing unsigned publications continue to work without a stamp.
