# Maps independent completion work — November 5, 2026

## Temporary trip nearby checkpoints (4013)

The current map census already records owner authorization for temporary per-trip opt-in Bluetooth (OD-MAP-5 and OD-TRIP-6). New code implements direct foreground peer checkpoint exchange. It never turns a radio signal into a GPS coordinate, proof-of-presence, stamp award, reciprocal sighting or public traveler pin. Multi-hop mesh relay and offline identity resolution are not claimed by this implementation.

The shared card is reachable in the Trip Crew section and an active trip-scoped Locate My Friends panel. It requires an explicit five-minute opt-in, describes the nearby/location OS permission, shows an active state and offers Stop. Blur, background, unmount, account/privacy-scope change, native failure and failed current server checks stop the session. Returning to the foreground does not restart it. Existing static capability baselines stay false; the native module reports actual device support separately from granted permission.

Migration4013 is generated by the Supabase CLI and normalized to repository ordering. It seeds `trip_nearby_checkpoints_enabled=false`. Enrollment is a service-only transaction with accepted role/status membership, current active account and Ghost Mode checks. Each participant separately consents; sessions last at most15minutes (the UI chooses5). A random service UUID rotates per trip minute, and per-participant64hex checkpoint tokens expire within60seconds. Tokens contain no person/trip IDs or coordinates; only hashes are stored. The HTTP schema refuses extra coordinates, stable subject IDs and background flags.

Every observation resolves the opaque token only to a current same-trip opted-in participant and rechecks blocks, account state, membership and directional trip hides. Only the observing member receives the result. Peer results expire within60seconds and the client removes them locally between refreshes. Owner revocation erases sessions/observations; a short-lived cancellation marker prevents a delayed start from resurrecting a stopped session. Profile deletion cascades retained source identity. A bounded retention sweep continues when the feature flag is off and reports through scheduler health; freshness checks do not depend on that sweep.

## Native radio implementation and local proof

`modules/portava-nearby-checkpoint` now contains actual CoreBluetooth and Android Bluetooth GATT engines plus Expo bridges. Both advertise only the rotating service UUID and read only the bounded opaque token. They cap peer/connection/read work, enforce wall and monotonic expiry, refuse late callbacks, and stop on background/destruction. No radio prompt occurs in capability reads. Android requests appropriate nearby/location permissions on explicit start without claiming `neverForLocation`; neither implementation reads GPS.

## Final controller replacement audit

A final independent read found a controller handoff race: a late native start resolution/rejection from an old session could stop the new controller's radio. The controller now fences native stop by current ownership, serializes radio release before another acquisition, and admits only the latest pending acquisition. The mounted card also ignores state/peer callbacks from a replaced controller. This changes no native radio protocol, feature flag, migration or consent duration. The focused controller, mounted card and Locate Friends lifecycle suites pass **17/17** checks (`/tmp/portava-nearby-controller-final-races.log`); source TypeScript also passes (`/tmp/portava-nearby-controller-types.log`). Deferred old-start resolution/rejection, competing acquisition, delayed radio release and retired UI callbacks are all covered.
